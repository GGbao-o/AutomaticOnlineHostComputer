# 打标机文件交互流程（当前前端引擎实现）

## 1. 范围与文件

1号线前天车在 `ST102`、2号线前天车在 `ST502` 使用各自配置的打标共享目录。当前生产流程直接使用 `3.txt`、`A.txt`、`B.txt`；通用的 `FileHandshakeClient` 中 `cmd.txt/ack.txt` 示例不是这两条生产前端流程的实际文件名。

| 文件 | 方向 | 当前生产含义 |
|---|---|---|
| `3.txt` | 打标机→上位机 | 打标机状态文件；前端在放板前读取，内容 `1` 才认为空闲可放板。 |
| `A.txt` | 上位机→打标机 | 打标任务。ASCII 编码，两行：第1行 `MarkingContent`，第2行工件 `Diameter`。 |
| `B.txt` | 打标机→上位机 | 打标完成回执。当前流程仅以文件存在作为完成条件，不解释内容。 |

共享目录可达性由 `MarkerShareMonitor` 在独立后台线程探测；探测结果用于可观测性，真正写A/读B仍由本次前天车业务动作执行。

## 2. 实际交接顺序

```text
确认 3.txt=1 且前天车/区域锁满足
  → 天车XY到打标位，Z下降并退磁放板
  → Z升安全 与 写入 A.txt 并行启动
  → 两者均成功返回后，每500ms轮询 B.txt，最长1小时
  → B.txt 出现：本次打标文件握手闭环
  → 天车Z下降、充磁、X11确认有板、Z升安全
  → 删除 B.txt，再进入中转架交接
```

`A.txt` 写成功只表示文件写入成功，不表示打标已经完成；只有 `B.txt` 在本轮出现才推进到取回工件。等待 B 的1小时不是“设备已加工完成”的通用证明，超时后工件可能仍在打标位，必须按现场状态确认。

## 3. 异常与状态未知

| 场景 | 当前代码行为 | 不能据此推断的事 |
|---|---|---|
| 共享目录不存在、认证/文件读写失败 | 当前动作抛异常，由前端引擎既有异常路径收尾与暂停处理。 | 不能据此认定工件还在原位或 A.txt 未被打标机读取。 |
| B.txt 一小时未出现 | 抛 `TimeoutException`，保留现场处置需求。 | 不能删除A或假定打标失败；需检查打标位实物与打标机。 |
| B.txt 旧残留 | 写 A 前先删除旧 B，避免把上一轮回执误认为本轮完成。 | 删除旧B不等于清除了上一轮工件或打标机内部任务。 |
| 取回时 X11 未确认 | 按前天车取料异常路径处理。 | B已出现只表示文件回执，不等于磁铁已经吸住工件。 |

前天车在打标区持有的 ZoneMT、前后天车与中转架的 ZoneTS/后续锁，按对应流程的 finally 释放。软件锁释放不表示天车位置或打标位工件已经物理安全。

| 位置 | 作用 |

| `Service/FlowEngine/Line2FrontFlowEngine.cs` | 2号线 ST502 的同型流程。 |
| `Communication/DeviceServices/MarkerShareMonitor.cs` | 共享目录后台探测与连接状态快照。 |
| `Communication/Clients/FileHandshakeClient.cs` | 通用文件握手封装；文件名/字段与当前前端生产流程不同，仅作通用能力参考。 |
