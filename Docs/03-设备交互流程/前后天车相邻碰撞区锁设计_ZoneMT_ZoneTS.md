# 前后天车相邻碰撞区锁设计（ZoneMT / ZoneTS）

> 文档状态：2026-07-08已按本文档完成代码实现。  
> 适用范围：1号线前天车、1号线后天车、2号线前天车、2号线后天车中与打号机、中转架、斜床1相邻区域有关的动作。  
> 设计目标：在不降低现场安全边界的前提下，减少原 `SharedAreaLock` 粒度过粗导致的低效率等待。

## 0. 代码实现位置

| 内容 | 实现位置 |
|---|---|
| 两把Zone锁定义 | `Service/FlowEngine/SafetyFlags.cs` |
| 1号线前天车打号/中转架持锁 | `Service/FlowEngine/Line1FrontFlowEngine.cs` |
| 2号线前天车打号/中转架持锁 | `Service/FlowEngine/Line2FrontFlowEngine.cs` |
| 1号线后天车上料/下料/应急 | `Service/FlowEngine/Line1RearFlowEngine.cs` |
| 2号线后天车上料/下料/应急 | `Service/FlowEngine/Line2RearFlowEngine.cs` |

实现后的关键规则：

1. 前天车打号阶段只持有`ZoneMT`。
2. 前天车进入中转架前再获取`ZoneTS`，中转架放料完成且Z安全后释放`ZoneTS + ZoneMT`。
3. 后天车进入中转架取料前获取`ZoneMT + ZoneTS`，并在锁内复核物理有板和软件缓存。
4. 后天车取中转架去普通斜床，Z安全后释放`ZoneTS + ZoneMT`。
5. 后天车取中转架去ST108/ST606，Z安全后释放`ZoneMT`，保留`ZoneTS`到斜床1交互退避完成。
6. ST108/ST606下料只持有`ZoneTS`。

## 1. 业务背景

当前前后天车在打号机、中转架、斜床1附近存在物理干涉风险。旧设计使用一把 `SharedAreaLock` 保护整片共享区域：

```text
打号机 + 中转架 + 斜床1
```

这种做法安全，但粒度过粗。典型低效率场景是：

1. 后天车正在斜床1执行下料或上料。
2. 后天车因为斜床1靠近中转架，持有 `SharedAreaLock`。
3. 前天车即使只是想去打号机，也会被 `SharedAreaLock` 阻塞。
4. 实际现场中，打号机和斜床1分处中转架两侧，二者本身并不直接碰撞。

真实物理关系更接近：

```text
左侧                                  中间                                  右侧

打号机 A       <-- 相邻会碰撞 -->       中转架 B       <-- 相邻会碰撞 -->       斜床1 C
```

因此真正需要互斥的不是“打号机、中转架、斜床1三者全部互斥”，而是两个相邻碰撞边界：

```text
A 与 B 不能同时进入。
B 与 C 不能同时进入。
A 与 C 可以同时工作。
```

这就是本设计拆分 `SharedAreaLock` 的原因。

## 2. 锁定义

### 2.1 天车自身锁

天车自身锁保持不变：

| 锁 | 含义 |
|---|---|
| `FrontCraneLock` | 前天车一次只能执行一个前端动作 |
| `RearCraneLock` | 后天车一次只能执行一个后端动作 |

天车自身锁只解决“同一台天车不能同时干两件事”，不表达打号机、中转架、斜床1之间的物理碰撞关系。

### 2.2 相邻碰撞区锁

新增或替代原共享区锁的两个概念锁：

| 锁名 | 简称 | 保护的物理边界 | 含义 |
|---|---|---|---|
| `MarkerTransferCollisionLock` | `ZoneMT` | 打号机 ↔ 中转架 | 防止一台天车在打号机附近，另一台天车同时进入中转架左侧碰撞范围 |
| `TransferSkew1CollisionLock` | `ZoneTS` | 中转架 ↔ 斜床1 | 防止一台天车在中转架附近，另一台天车同时进入斜床1右侧碰撞范围 |

### 2.3 各位置应持锁关系

| 天车所在或准备进入的位置 | 必须持有的碰撞区锁 |
|---|---|
| 打号机 | `ZoneMT` |
| 中转架 | `ZoneMT + ZoneTS` |
| 斜床1（1号线 ST108 / 2号线 ST606） | `ZoneTS` |
| 普通斜床（非 ST108/ST606） | 不需要 `ZoneMT` / `ZoneTS` |
| 动平衡下料架、研磨上料架等远离该区域的位置 | 不需要 `ZoneMT` / `ZoneTS`，仍使用原目的地位置锁 |
| 已离开相邻碰撞边界的安全区 | 不持有碰撞区锁 |

## 3. 中转架缓存与槽位互斥规则

如果中转架操作被严格定义为必须同时持有 `ZoneMT + ZoneTS`，则原 `_transferRackLock` 不再需要作为业务互斥锁。

原因是：

```text
进入中转架 = 必须同时拿到 ZoneMT + ZoneTS
```

只要所有中转架物理槽位读写、软件缓存读写都放在 `ZoneMT + ZoneTS` 持锁期间完成，前天车和后天车就不可能同时修改中转架状态。

但这要求代码遵守一条硬规则：

> 锁前判断只能作为候选判断；真正进入中转架后，必须重新读取物理信号并重新核对软件缓存。

也就是说，不能写成：

```text
锁前看到中转架1有空
拿到 ZoneMT + ZoneTS
直接去中转架1放料
```

必须写成：

```text
锁前看到中转架可能有空
拿到 ZoneMT + ZoneTS
重新读取中转架物理有板信号
重新核对软件缓存
重新选择可用槽位
再执行放料
```

后天车取料同理：

```text
锁前看到中转架有板且缓存有工件
拿到 ZoneMT + ZoneTS
重新读取物理有板信号
重新核对软件缓存
重新匹配目标斜床是否仍可加工
再执行取料
```

如果实现阶段为了降低一次性改动风险，也可以短期保留 `_transferRackLock` 作为内部数据保护锁，但它不应再作为“进入中转架区域”的前置业务锁。最终设计中，`ZoneMT + ZoneTS` 就是中转架互斥边界。

## 4. 全局防死锁顺序

所有需要多把锁的流程，必须使用统一获取顺序：

```text
天车自身锁
→ ZoneMT
→ ZoneTS
→ 目的地专用位置锁
```

禁止出现：

```text
先持有 ZoneTS，再等待 ZoneMT
```

原因是：

1. 前天车去中转架时可能已经持有 `ZoneMT`，正在等待 `ZoneTS`。
2. 如果后天车从斜床1方向出来时已经持有 `ZoneTS`，又反向等待 `ZoneMT`。
3. 两边就会形成死锁。

因此，从斜床1出来后如果下一步确实还要进入中转架方向，必须先释放旧的 `ZoneTS`，再按 `ZoneMT → ZoneTS` 顺序重新申请。

释放顺序建议与获取顺序相反：

```text
先释放 ZoneTS
再释放 ZoneMT
最后释放天车自身锁
```

实际代码中也可以使用动作任务牌记录“当前动作实际持有哪些锁”，然后在 finally 或应急里幂等释放，避免重复 Release 导致信号量计数异常。

## 5. 锁释放的现场确认原则

本项目按现场确认策略执行：

> 只要天车Z轴已经升到0位或配置的安全高度，即可释放对应碰撞区锁；不需要等天车X/Y完全归位或完全离开区域。

原因是现场物理关系已经确认：

1. 前天车在中转架放料后，只要Z轴升到0位，天车处于高位安全状态。此时释放 `ZoneMT + ZoneTS` 后，前天车马上执行X向安全/归位方向移动；只要天车本身没有故障，不会与后天车发生碰撞。
2. 后天车在中转架取料后，只要Z轴升到0位，板已经离开中转架低位交互区域。此时去普通斜床可以直接释放 `ZoneMT + ZoneTS`；去斜床1则释放 `ZoneMT`、继续持有 `ZoneTS`。
3. 后天车在斜床1上料或下料完成后，仍需要按原ST108/ST606策略执行X+1000或配置退避。该阶段释放 `ZoneTS` 的条件仍是完成斜床1侧退避或进入异常人工确认逻辑。

更具体地说：

| 场景 | 释放条件 |
|---|---|
| 前天车中转架放料 | 放板完成，Z轴升到0位或配置安全高度后，释放 `ZoneTS` 和 `ZoneMT` |
| 后天车中转架取料 → 普通斜床 | 取板完成，X11确认有板，Z轴升到0位或配置安全高度后，释放 `ZoneTS` 和 `ZoneMT` |
| 后天车中转架取料 → 斜床1 | 取板完成，X11确认有板，Z轴升到0位或配置安全高度后，释放 `ZoneMT`，继续持有 `ZoneTS` |
| 后天车斜床1上料/下料 | 斜床1交互完成后，执行X+1000或配置退避；退避完成后释放 `ZoneTS` |

因此本文档后续流程中的“释放锁”均按上述现场策略理解。锁释放后，天车可能还没有完全回到home，但Z轴已经处于安全高度，正常天车移动不会造成碰撞。

需要特别说明的是：如果释放锁之后天车自身移动失败、通信中断、伺服报警或位置异常，这已经不是正常互斥逻辑问题，而是设备异常。此时必须暂停引擎并弹窗，要求人工确认现场。

```text
锁已释放 = 软件允许其它流程继续判断进入。
锁已释放 ≠ 天车已经完成归位。
若释放锁后天车移动失败，必须按设备异常暂停弹窗处理。
```

## 6. 流程1：前天车 Pos3取料 → 打号机 → 中转架放料 → 归位

### 6.1 业务目标

前天车从货叉 Pos3 取到板后，先送到打号机打号；打号机文件握手完成后，前天车再从打号机吸回板，送到本线中转架空位，并通知后天车侧缓存。

### 6.2 持锁流程

```text
① Pos3 取料
   持锁：FrontCraneLock
   碰撞区锁：无

   前天车移动到 Pos3。
   Z下降。
   充磁吸板。
   读取 X11=1 确认天车确实吸住板。
   Z升到安全高度。

② 粗判断中转架是否可能有空位
   持锁：FrontCraneLock
   碰撞区锁：无

   此处只做候选判断，不能作为最终放料位置。
   因为后天车可能在之后先进入中转架取走或状态变化。

③ 进入打号机区域前申请 ZoneMT
   持锁：FrontCraneLock + ZoneMT

   申请 ZoneMT 成功后，表示前天车可以进入打号机侧。
   此时后天车不能进入中转架，因为中转架需要 ZoneMT + ZoneTS。
   但后天车仍可以在斜床1区域工作，因为斜床1只需要 ZoneTS。

④ 打号机放板并等待文件握手
   持锁：FrontCraneLock + ZoneMT

   前天车飞到打号机。
   Z下降。
   退磁放板。
   Z上升到安全高度。
   写 A.txt 或对应请求文件。
   等待 B.txt 或打号机完成文件。

   注意：等待 B.txt 可能耗时较长，但此阶段只持有 ZoneMT，不持有 ZoneTS。
   因此后天车在斜床1下料或上料不会被阻塞。

⑤ 打号完成后从打号机取回板
   持锁：FrontCraneLock + ZoneMT

   Z下降。
   充磁。
   读取 X11=1 确认吸住板。
   Z升到安全高度。

⑥ 准备进入中转架，申请 ZoneTS
   持锁：FrontCraneLock + ZoneMT + ZoneTS

   前天车要从打号机进入中转架。
   中转架位于两个碰撞边界中间，因此必须同时持有 ZoneMT 和 ZoneTS。

   拿到 ZoneTS 后，必须重新读取中转架物理信号 不需要读软件缓存 有缓存也不管 只要信号没板就
   如果没有空位，不能继续放料，应暂停或退出本次放料逻辑，由现场处理或等待下一轮。

⑦ 中转架放料
   持锁：FrontCraneLock + ZoneMT + ZoneTS

   重新选择实际空位。
   前天车飞到对应中转架位置。
   Z下降。
   退磁放板。
   写入或通知后端缓存，记录该槽位对应的工件数据。
   Z升到0位或配置的安全高度。

⑧ Z升到0位或配置安全高度后释放 ZoneTS 和 ZoneMT
   持锁释放策略：
   - 前天车中转架放料完成后，Z轴升到0位或配置安全高度，即可释放 ZoneTS 和 ZoneMT。
   - 不需要等待前天车X/Y完全归位后再释放。
   - 释放后前天车继续执行 X→homeX / Z→home 或后续归位动作。
   - 如果释放锁后天车移动失败，按天车异常暂停弹窗处理。

⑨ 归位
   持锁：FrontCraneLock
   碰撞区锁：无

   前天车 X→homeX。
   Z→home 或确认Z在安全高度。
   动作完成后释放 FrontCraneLock。
```

### 6.3 该流程带来的效率变化

旧模型中，前天车打号等待 B.txt 时持有 `SharedAreaLock`，后天车不能进 ST108/ST606。

新模型中，前天车打号只持有 `ZoneMT`，后天车在 ST108/ST606 只需要 `ZoneTS`，所以二者可以并行。

## 7. 流程2：后天车 中转架取料 → 普通斜床

### 7.1 业务目标

后天车从中转架取走一块板，送到非斜床1的普通斜床。普通斜床与打号机、中转架、斜床1相邻碰撞区域无关，因此离开中转架后不需要继续持有 `ZoneMT` 或 `ZoneTS`。

### 7.2 持锁流程

```text
① 粗判断是否存在可上料配对
   持锁：无

   判断内容包括：
   - 中转架物理上可能有板；
   - 软件缓存存在对应工件；
   - 存在空闲且请求数据/请求上料的斜床；
   - 目标斜床最大可加工长度满足当前工件；
   - 后天车没有被暂停。

   该判断只是候选判断，不能作为最终取料依据。

② 后天车申请 RearCraneLock
   持锁：RearCraneLock

   确保后天车一次只执行一个动作。

③ 进入中转架前申请 ZoneMT → ZoneTS
   持锁：RearCraneLock + ZoneMT + ZoneTS

   中转架处于打号机和斜床1之间，因此必须同时持有 ZoneMT 和 ZoneTS。

④ 中转架内重新确认物理板和软件缓存
   持锁：RearCraneLock + ZoneMT + ZoneTS

   重新读取中转架物理有板信号。
   重新确认该槽位软件缓存仍存在。
   重新匹配目标斜床仍可加工该板。
   如果任一条件变化，放弃本次动作，释放锁后进入下一轮。

⑤ 中转架取料
   持锁：RearCraneLock + ZoneMT + ZoneTS

   后天车飞到中转架槽位。
   Z下降。
   充磁。
   多次确认 X11=1，确认天车吸住板。
   Z升到0位或安全高度。
   从中转架缓存中移除该工件，或标记该工件已被后天车取走。

⑥ Z升到0位或配置安全高度后释放 ZoneTS 和 ZoneMT
   持锁：RearCraneLock
   碰撞区锁：无

   普通斜床不需要 ZoneMT 或 ZoneTS。
   因此后天车从中转架取完板，X11确认吸住，Z轴升到0位或配置安全高度后，直接释放 ZoneTS 和 ZoneMT。
   不需要等后天车飞到普通斜床或离开中转架X/Y边界后再释放。
   如果释放锁后后天车移动失败，按天车异常暂停弹窗处理。

⑦ 飞普通斜床并执行上料握手
   持锁：RearCraneLock
   碰撞区锁：无

   后天车飞到普通斜床。
   Z下降。
   与CNC执行上料握手。
   退磁放板。
   Z升。
   根据原业务更新斜床状态和工件缓存。

⑧ 归位并释放 RearCraneLock
   持锁：无
```

## 8. 流程3：后天车 中转架取料 → 斜床1（ST108 / ST606）

### 8.1 业务目标

后天车从中转架取板后送到斜床1。斜床1位于中转架右侧，取中转架时需要 `ZoneMT + ZoneTS`。取板完成、X11确认有板、Z轴升到0位或配置安全高度后，可以释放 `ZoneMT`，继续持有 `ZoneTS`。

这样前天车可以提前进入打号机工作。

### 8.2 持锁流程

```text
① 粗判断中转架有板、缓存存在、斜床1可加工
   持锁：无

   斜床1必须满足：
   - 状态允许上料；
   - 请求数据/请求上料信号满足；
   - 当前工件长度不超过该斜床配置的最大加工长度；
   - CNC通信可用。

② 后天车申请 RearCraneLock
   持锁：RearCraneLock

③ 进入中转架前申请 ZoneMT → ZoneTS
   持锁：RearCraneLock + ZoneMT + ZoneTS

④ 中转架内重新确认取料条件
   持锁：RearCraneLock + ZoneMT + ZoneTS

   重新读取中转架物理信号。
   重新核对软件缓存。
   重新确认斜床1仍然可接收该工件。

⑤ 中转架取料
   持锁：RearCraneLock + ZoneMT + ZoneTS

   飞中转架。
   Z下降。
   充磁。
   X11多次确认有板。
   Z升到0位或安全高度。
   中转架缓存移除或标记取走。

⑥ Z升到0位或配置安全高度后释放 ZoneMT
   持锁：RearCraneLock + ZoneTS

   释放 ZoneMT 后，前天车可以进入打号机。
   后天车仍持有 ZoneTS，因此前天车不能进入中转架，其他后天车动作也不能进入中转架/斜床1边界。

   现场策略明确：后天车从中转架取完板，X11确认有板，Z轴升到0位或配置安全高度后即可释放 ZoneMT。
   不需要等后天车先朝斜床1方向移动一段距离。
   这样前天车可以尽快进入打号机，提高并行效率。

⑦ 飞斜床1并执行上料握手
   持锁：RearCraneLock + ZoneTS

   飞 ST108 或 ST606。
   Z下降。
   执行CNC上料握手。
   退磁放板。
   等待或确认CNC收板完成。
   Z升。

⑧ X+1000 或配置退避动作
   持锁：RearCraneLock + ZoneTS

   退避目的是让后天车离开斜床1与中转架的相邻碰撞边界。
   退避成功后，才认为可以释放 ZoneTS。

⑨ 释放 ZoneTS，归位并释放 RearCraneLock
   持锁：无
```

### 8.3 该流程带来的效率变化

旧模型中，后天车从中转架取板后送斜床1，全程持有 `SharedAreaLock`，前天车不能打号。

新模型中，后天车从中转架取完板并Z升到0位或配置安全高度后释放 `ZoneMT`，前天车即可进入打号机；后天车继续持有 `ZoneTS` 完成斜床1交互。这样打号机和斜床1可以更早并行。

## 9. 流程4：后天车 斜床1下料 → 目的地

### 9.1 业务目标

斜床1加工完成后，后天车从 ST108 或 ST606 下料。因为斜床1只与中转架发生相邻碰撞，不与打号机直接碰撞，所以斜床1下料只需要 `ZoneTS`。

### 9.2 持锁流程

```text
① 判断斜床1是否可下料
   持锁：无

   条件包括：
   - 斜床状态为 WaitingUnload 或代码中对应的待下料状态；
   - bed.Wp 存在；
   - 完工记录可写；
   - 目的地允许放板；
   - 后天车未暂停。

② 后天车申请 RearCraneLock
   持锁：RearCraneLock

③ 进入斜床1前申请 ZoneTS
   持锁：RearCraneLock + ZoneTS

   此时前天车仍可以在打号机工作，因为打号机只需要 ZoneMT。
   但前天车不能进入中转架，因为中转架需要 ZoneMT + ZoneTS。

④ 斜床1下料
   持锁：RearCraneLock + ZoneTS

   飞 ST108 或 ST606。
   X11清检，确认天车当前没有误吸板。
   Z下降。
   充磁。
   X11多次确认吸住板。
   Z升。
   与CNC执行下料完成握手。

⑤ X+1000 或配置退避动作
   持锁：RearCraneLock + ZoneTS

   后天车退离斜床1与中转架的碰撞边界。
   退避成功后释放 ZoneTS。

⑥ 释放 ZoneTS
   持锁：RearCraneLock
   碰撞区锁：无

⑦ 飞目的地
   持锁：RearCraneLock + 目的地专用位置锁

   如果目的地是 M817、M720、M818、M821 等下游位置，继续沿用原有目的地锁。
   此阶段通常不需要 ZoneMT 或 ZoneTS。

⑧ 目的地放板，归位并释放 RearCraneLock
   持锁：无
```

### 9.3 目的地如果需要经过中转架方向

如果未来新增某个目的地，必须经过或进入中转架碰撞范围，则不能在持有 `ZoneTS` 的情况下直接等待 `ZoneMT`。

必须按以下流程：

```text
斜床1下料完成
X+1000退避
释放 ZoneTS
重新申请 ZoneMT
再申请 ZoneTS
进入中转架方向
完成目的地放板
释放 ZoneTS
释放 ZoneMT
```

这样可以避免“前天车持 ZoneMT 等 ZoneTS，后天车持 ZoneTS 等 ZoneMT”的死锁。

## 10. 异常处理原则

### 10.1 所有异常都必须记录当前实际持锁

后端动作建议继续使用类似 `EmergencyActionLease` 的动作任务牌，记录当前动作实际持有的锁：

```text
RearCrane
ZoneMT
ZoneTS
M817 / M720 / M818 / M821
```

前端动作也建议明确记录：

```text
FrontCrane
ZoneMT
ZoneTS
```

释放锁时只能释放“本动作实际持有”的锁，不能猜测释放。否则 `SemaphoreSlim.Release()` 可能把计数放大，导致两个动作同时进入同一区域。

### 10.2 Z轴已经下降或可能下降时，不允许盲目横移退避

如果异常发生时 Z轴已经下降，或者程序无法确认 Z轴是否在安全高度，则不能为了释放碰撞区锁而盲目执行 X/Y 横移。

此时处理策略应为：

```text
暂停引擎
弹窗说明：
  - 哪个流程异常；
  - Z轴安全状态是否明确；
  - 哪些锁已经释放；
  - 哪些锁因为安全原因无法通过退避确认；
  - 要求人工确认现场后再恢复。
```

### 10.3 锁释放不等于物理安全

当异常 finally 释放 `ZoneMT` 或 `ZoneTS` 时，弹窗必须说清楚：

```text
软件碰撞锁已释放。
但由于退避失败、位置读取失败或Z轴状态不明确，不能证明天车已经离开物理碰撞边界。
请人工确认现场安全后再继续。
```

这条文案非常重要，避免现场把“锁已释放”理解成“天车已经安全离开”。

### 10.4 打号机等待异常

前天车等待打号机 B.txt 或文件完成时，只持有 `ZoneMT`。

如果等待超时或文件异常：

1. 前天车应暂停。
2. 弹窗说明打号机文件握手异常。
3. 根据天车是否仍在打号机区域决定是否释放 `ZoneMT`。
4. 不应影响后天车在斜床1侧的 `ZoneTS` 动作。

如果天车仍在打号机上方，但 Z轴安全，现场策略允许释放 `ZoneMT`，弹窗必须说明天车可能仍在打号机区域。

### 10.5 中转架取放异常

中转架动作持有 `ZoneMT + ZoneTS`。

异常时必须说明：

```text
当前动作发生在中转架。
中转架左右两侧碰撞边界都受影响。
ZoneMT/ZoneTS是否已释放。
中转架缓存是否已经写入或删除。
物理板是否可能已经放下或取走。
```

如果异常发生在“软件缓存已写，但物理放板未确认”或“物理取板已完成，但缓存删除失败”之间，必须暂停并要求人工核对中转架物理有板与软件缓存。

### 10.6 斜床1上料/下料异常

斜床1动作只需要 `ZoneTS`。

异常时应沿用目前 ST108/ST606 的安全策略：

1. 如果 Z轴未下降，可以尝试按配置退避，例如 X+1000。
2. 如果 Z轴已经下降或无法确认，不执行横移退避。
3. 无论是否退避成功，最终是否释放 `ZoneTS` 必须在弹窗中写清。
4. 弹窗要求人工确认现场后执行斜床应急或恢复。

## 11. 应急处理要求

### 11.1 斜床应急

斜床应急需要显示并处理：

```text
RearCraneLock
ZoneMT
ZoneTS
目标斜床状态
目标斜床工件缓存
当前动作任务牌
```

对于 ST108/ST606：

| 动作阶段 | 可能持有的锁 |
|---|---|
| 中转架取料阶段 | `RearCrane + ZoneMT + ZoneTS` |
| 从中转架去斜床1途中 | `RearCrane + ZoneTS` |
| 斜床1上料/下料交互 | `RearCrane + ZoneTS` |
| 退避完成后 | 通常只剩 `RearCrane` 或无碰撞区锁 |

斜床应急释放锁时，必须根据任务牌实际持有情况释放，不能固定释放全部锁。

### 11.2 前端在途应急

前端在途应急需要增加对 `ZoneMT` 和 `ZoneTS` 的诊断说明：

| 前端阶段 | 可能持有的锁 |
|---|---|
| Pos3取料 | `FrontCrane` |
| 打号机放板/等待文件/取回 | `FrontCrane + ZoneMT` |
| 中转架放料 | `FrontCrane + ZoneMT + ZoneTS` |
| 离开中转架后归位 | `FrontCrane` |

如果前天车异常停在打号机，只影响 `ZoneMT`。

如果前天车异常停在中转架，则同时影响 `ZoneMT` 和 `ZoneTS`，必须人工确认中转架左右两侧都安全。

## 12. 日志与弹窗建议

日志和弹窗不要再笼统写“共享区锁”，应明确写：

```text
ZoneMT（打号机-中转架碰撞区）
ZoneTS（中转架-斜床1碰撞区）
```

示例：

```text
[Line1Rear] ST108下料异常：Z轴可能已下降，未执行X退避。
软件锁已释放：RearCrane=True, ZoneTS=True。
注意：ZoneTS已释放不代表后天车已离开ST108-中转架碰撞边界。
请人工确认现场安全后执行斜床应急恢复。
```

中转架异常示例：

```text
[Line1Front] 中转架放料异常：物理放板结果不确定。
当前动作发生在中转架，涉及 ZoneMT 和 ZoneTS。
软件缓存状态：ST105已写入工件 xxx。
请人工核对ST105是否有板，确认后使用前端在途应急处理。
```

## 13. 后天车动态调度与Zone锁关系（2026-07-08补充）

本次后天车调度不再写死“先下料、再上料”，而是在主循环中先生成候选，再决定本轮动作。

调度层只做三件事：

1. 生成上料候选；
2. 生成下料候选；
3. 根据候选压力选择本轮执行上料、下料或等待。

调度层不直接移动天车、不写PLC、不释放Zone锁。真正的动作仍由 `DoLoad` 和 `DoUnload` 执行，因此正常业务步骤、坐标公式、信号地址和异常收尾策略保持不变。

### 13.1 上料候选

上料候选由“中转架工件 + 可加工斜床”组成，必须满足：

- 中转架物理有板；
- 后端软件缓存存在；
- 斜床连接正常；
- 本轮信号新鲜；
- 斜床处于Idle；
- CNC请求数据；
- `skewBed.maxWorkpieceLengthMm` 能加工该工件长度。

中转架按前天车放板到达顺序扫描。当前没有任何可用斜床能加工的板，可以在候选期间跳过，不阻塞后面可加工的板。例如第一块板过长，而第二块板当前有斜床可加工，则第二块板可以先生成上料候选。

但如果多块板都可加工，仍按到达顺序，不为了效率打乱可加工工件之间的顺序。

### 13.2 下料候选

下料候选必须满足：

- 斜床处于WaitingUnload；
- 斜床保存的 `Wp` 工件身份存在；
- 完工记录已写入或本轮写入成功；
- 目标下料位允许放料；
- 本轮信号新鲜。

ST108/ST606下料只持有 `ZoneTS`。因此后天车在斜床1下料时，前天车仍可在打号机持 `ZoneMT` 工作，但不能进入中转架，因为中转架需要 `ZoneMT + ZoneTS`。

### 13.3 决策规则

决策顺序如下：

1. 没有下料候选，但有上料候选：执行上料。
2. 没有上料候选，但有下料候选：执行下料。
3. 中转架物理满3个，并且存在上料候选：强制上料。
4. 中转架可匹配板数 ≥ 2，并且下料候选少于高下料压力阈值：优先上料。
5. 下料候选数达到高下料压力阈值，并且中转架可匹配板数 ≤ 1：优先下料。
6. 其他普通情况：默认下料优先。

其中，中转架容量固定为3，因此中转架压力使用固定值；斜床可能坏掉或断线，因此下料压力阈值按有效斜床数量动态折算：

| 有效斜床数量 | 高下料压力阈值 |
|---|---:|
| 0~1台 | 1 |
| 2~3台 | 2 |
| 4~5台 | 3 |

有效斜床指本轮连接正常且信号新鲜的斜床。断线、坏床、信号读取失败的斜床不参与压力基数，避免现场坏1~2台斜床时仍死等3台同时下料。

### 13.4 与Zone锁的边界

动态调度只决定“本轮选择上料还是下料”。Zone锁仍在动作内部获取和释放：

- 上料进入中转架：`DoLoad` 内部获取 `ZoneMT -> ZoneTS`；
- 去普通斜床：中转架取完板、X11确认、Z安全后释放 `ZoneTS + ZoneMT`；
- 去ST108/ST606：中转架取完板、X11确认、Z安全后释放 `ZoneMT`，保留 `ZoneTS` 到斜床1交互退避完成；
- ST108/ST606下料：只获取 `ZoneTS`，退避完成后释放。

因此，调度算法提高的是“后天车选任务”的效率，不改变物理碰撞区安全模型。

## 14. 对现有代码的改动范围

本设计落地时，主要会影响以下代码区域：

| 区域 | 改动内容 |
|---|---|
| `SafetyFlags` | 用 `ZoneMT`、`ZoneTS` 替代或扩展当前 `SharedAreaLock` |
| 1/2号线前端引擎 | 打号机阶段只拿 `ZoneMT`；中转架阶段拿 `ZoneMT + ZoneTS` |
| 1/2号线后端上料 | 普通斜床取中转架后释放两区锁；斜床1取中转架后释放 `ZoneMT`、保留 `ZoneTS` |
| 1/2号线后端下料 | ST108/ST606下料只拿 `ZoneTS` |
| 斜床应急 | 从释放 `SharedArea` 改为按任务牌释放 `ZoneMT`/`ZoneTS` |
| 前端在途应急 | 增加 `ZoneMT`/`ZoneTS` 诊断 |
| 异常弹窗 | 明确哪一把碰撞区锁已释放、是否完成物理退避 |
| docs文档 | 替换“共享区锁”粗粒度描述，说明相邻碰撞区锁模型 |

## 15. 设计收益

### 15.1 提升并行效率

允许：

```text
前天车在打号机
后天车在斜床1
```

同时执行。

这能解决原来后天车 ST108/ST606 动作占用 `SharedAreaLock` 时，前天车连打号机都进不去的问题。

### 15.2 安全边界更贴近现场

锁的含义从“一个大共享区”变成“两个相邻碰撞边界”：

```text
打号机 ↔ 中转架
中转架 ↔ 斜床1
```

现场人员和代码日志都更容易理解到底是哪一段区域被占用。

### 15.3 异常弹窗更准确

原来只说“共享区锁释放/未释放”，无法表达是打号机侧风险还是斜床1侧风险。

新模型可以明确：

```text
ZoneMT异常：打号机-中转架侧需要确认。
ZoneTS异常：中转架-斜床1侧需要确认。
ZoneMT+ZoneTS异常：天车在中转架，需要左右两侧都确认。
```

## 16. 实施前必须确认的现场条件

正式改代码前，需要现场确认以下条件：

1. 前天车在打号机区域时，后天车在 ST108/ST606 区域动作确实不会互相碰撞。
2. 后天车在 ST108/ST606 区域时，前天车只进入打号机、不进入中转架，确实安全。
3. 中转架位置必须同时阻断打号机侧和斜床1侧，即中转架动作必须持有 `ZoneMT + ZoneTS`。
4. 现场已确认：前天车中转架放料后Z升0即可释放 `ZoneMT + ZoneTS`；后天车中转架取料后Z升0，去普通斜床释放 `ZoneMT + ZoneTS`，去斜床1释放 `ZoneMT` 并保留 `ZoneTS`。
5. 如果释放锁后天车归位或横移动作失败，弹窗必须提示“锁已释放但天车未完成后续移动”，并暂停引擎等待人工确认。

## 17. 最终推荐方案

推荐最终落地模型如下：

```text
打号机动作：
  持 ZoneMT

中转架动作：
  持 ZoneMT + ZoneTS

斜床1动作：
  持 ZoneTS

普通斜床动作：
  不持 ZoneMT / ZoneTS

中转架缓存和槽位读写：
  必须在 ZoneMT + ZoneTS 持锁期间重新确认并更新

锁释放：
  按实际物理离开碰撞边界释放；
  若按现场策略提前释放，必须暂停弹窗说明物理风险。
```

这套模型能满足“打号机和斜床1可并行、中转架作为中间危险区左右互斥”的需求，同时保留异常和应急处理的可解释性。
