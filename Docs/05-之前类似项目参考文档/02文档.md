```markdown
## 一、设备通用状态模型

每台设备是被动执行方，不主动控制天车。天车是唯一主动搬运者。设备的角色是：接收加工数据 → 执行加工 → 返回状态信号。

### 设备通用生命周期

```
空闲(idle=1) → 天车预约(Reservation=1) → 天车上料 → 夹紧 → 加工中 → 加工完成(over=1)
→ 天车预约(Reservation=1) → 天车下料 → 松开 → 空闲(idle=1)
```

### 设备内部状态机（PLC端需要实现的逻辑）

| 状态 | 条件 | 含义 |
|------|------|------|
| 空闲 | idle=1 且 over=0 | 可接收新工件 |
| 已预约 | 天车写了 Reservation=1 | 被某天车锁定，不可再分配 |
| 天车靠近 | 收到"天车已靠近"信号 | 准备上料/下料 |
| 夹紧中 | 收到工件 → 执行夹紧 | 夹紧完成 → 已夹紧=1 |
| 加工中 | 夹紧完毕 → 开始加工 | idle=0, over=0 |
| 加工完成 | 工艺完成 | over=1 → 等待天车下料 |
| 松开中 | 收到"天车下料到位" | 松开工件 |
| 已松开 | 松开工件完毕 | 天车取走工件 |

## 三、调度系统如何选择设备和天车

### 3.1 每500ms扫描一次

```
ScheduledTasks() 主循环:
├── 遍历 ListMachineSta (所有机器)
│   ├── 读 101 → idle   (空闲?)
│   ├── 读 102 → err    (检修?)
│   ├── 读 103 → over   (加工完成?)
│   └── 读 120 → reservation (已预约?)
│
├── 分类到4个列表:
│   ├── ListMachineOver   ← over=1 且未预约 且未检修 (需要下料!)
│   ├── ListMachineIDLE   ← idle=1 且未预约 且未检修 (可以上料!)
│   ├── ListMachineBusy   ← 忙碌中
│   └── ListMachineReservation ← 已预约，跳过
│
├── 生成搬运任务:
│   ├── 遍历 Over 列表 → 根据工艺路线找下一道空闲机器 → 生成 CraneTaskInfo
│   └── 遍历上料架(有板) → 找第一道工序空闲机器 → 生成 CraneTaskInfo
│
├── 路权冲突检测 → 过滤冲突任务
├── 分配空闲天车 → 检查天车可达范围
├── 障碍物检测 → 判断是否需要让路
└── 启动 CraneTask(天车, 任务) 或 CraneMovePosX(天车, 位置)
```

### 3.2 生成搬运任务的条件

```
// 条件1: 机器加工完成 → 需要下料
if (over == 1 && err == 0 && Reservation == 0)  // → MachineSta = 1

// 条件2: 机器空闲 → 可以上料
if (idle == 1 && over == 0 && err == 0 && Reservation == 0)  // → MachineSta = 2

// 生成任务时:
// 源设备=Over列表中的机器, 目标设备=下一道工序的空闲机器
// 判断: 目标机器的 MachineType == 下一道工序需要的 MachineTypeID
// 判断: 源设备和目标设备不在同一个STHash中(防止重复)
```

### 3.3 分配天车的条件

```
// 天车可达条件:
if (天车运动范围.StartX <= 任务路径.StartX) && (天车运动范围.EndX >= 任务路径.EndX)

// 同一任务路径如果有其他天车挡路 → 挡路天车移到外部 + 执行 CraneMovePosX
// 路权区间不重叠
```

## 四、各设备类型的具体业务逻辑

### 4.1 上下料架 (MaterialRack) — 工件入口/出口

**业务角色:** 工件的起点和终点

**上料架 (MachineType=1):**
- 有板时: 从 `TaskBordID` 中取任务 → 生成 `CraneTask(上料架→第一道工序机器)`
- 板被取走后: 任务从 `TaskBordID` 中移除

**下料架 (MachineType=2):**
- 天车放到下料架后: 触发"天车上料完成"信号
- 有板时: `TaskBordID` 移除 → `TaskInfo` 移除 → 数据库删除 → 任务完结

**关键逻辑:**
```
// 上料架: 遍历所有未开始的任务，匹配第一道工序
if (MachineType == 1) {  // 上料架
for (遍历 TaskBordID) {
if (WorkShip[0].MachineTypeID == 1) {  // 第一道工序是"上料"类型
// 找下一道工序的空闲机器
int mid = WorkShip[1].MachineTypeID;
int MidleID = FineIDLEMachine(mid, ListMachineIDLE);
if (MidleID != -1) → 生成搬运任务
}
}
}

// 下料架: 工件到达后直接删除
if (MachineType == 2) {  // 下料架
TaskBordID.Remove(工件ID);
TaskInfo.Remove(工件ID);
SoftDB.DeleteWorkInfo(工件ID);  // 从数据库删除
}
```

### 4.2 打标机 (MarkingMachine) — 工件打标

**业务角色:** 在版辊上打印标识

**天车上料时写入:**
- 外径 → 寄存器6
- 内径 → 寄存器7
- 打印内容(UTF8字符串) → 寄存器9起, 多寄存器写入

**PLC读取这些数据 → 执行打标 → 打标完成后:**
- 状态寄存器[0] → 空闲标志
- 状态寄存器[1] → 加工完成标志
- 其他状态位

**打标完成 → over=1 → 调度系统生成下料+下一道工序搬运任务**

**PLC需要的逻辑:**
1. 收到"天车上料到位" → 启动夹紧 → 已夹紧=1
2. 天车退磁离开后 → 收到"天车上料完成" → 开始打标
3. 打标完成 → over=1
4. 收到"天车下料到位" → 松开工件 → 已松开=1

| 功能 | 寄存器地址 |

| 下料完成=1 | 14631 |

| 下料到达松开位置=1 | 14629 |

**PLC通过35个寄存器(14603起)返回状态:**
- 14603+0 → 请求上料?
- 14603+1 → 已夹紧?
- 14603+2 → 请求下料?
- 14603+3 → 已松开?
- ...其他状态...

**研磨机PLC端完整动作逻辑:**

```

等待: 天车预约(Reservation=1)

状态1_等待上料:

状态2_天车上料到位:
条件: 收到"天车上料到位"=1 (14625)

状态3_等待天车离开:
条件: 收到"天车上料完成"=1 (14627) + "天车已远离"=1
动作: 开始研磨加工
反馈: idle=0 (忙碌)

状态4_加工中:
动作: 执行研磨工艺
完成后: over=1

状态5_等待下料:
条件: over=1, 天车已预约
等: 天车靠近

状态6_天车下料到位:
条件: 收到"天车下料到位"=1 (14629)
动作: 松开工件
反馈: 已松开=1

状态7_天车取走:
条件: 收到"天车下料完成"=1 (14631)
动作: 复位
反馈: idle=1, over=0
```

## 五、设备状态判断公式机制

所有状态(101-120)通过公式计算，公式存在数据库 `MachinePara` 表中：

**公式格式:** `{@线号}运算符值:显示文字:R,G,B`

**例子1:**
```
{@XC1YSK}==1:已松开:255,0,255
│        │   │       │
│        │   │       └── RGB颜色
│        │   └── 显示文字
│        └── 判断条件
└── 线号,通过DataPool查PLC寄存器值
```

**例子2:**
```
{@XC1WZFK}:尾座分开:0,255,0
│        │       │
│        │       └── 颜色
│        └── 显示文字,无判断条件(值>0即true)
└── 线号
```

**公式解析过程:**
1. `CalPara(exp)` → 将中缀表达式转为后缀
2. `{@线号}` → 查 `DataPool.getLineAddr("线号")` 得到完整地址 `0xCCAAAAAA`
3. 地址高8位 → 控制器ID → `controlHash` 找到设备
4. 地址低24位 → 具体Modbus寄存器地址
5. `Read(寄存器)` → 设备返回Modbus值
6. 代入公式计算 → 返回结果

## 六、完整工件生命周期

```
1. 操作员添加任务(FmAddTask)
   ├── 版辊编号 + 内外径 + 长度 + 堵头厚度 + 内孔斜度 + 打印内容
   ├── 选择工艺(决定工序路线)
   ├── 选择起始工序
   └── 存数据库 WorkInfoList

2. 上料架有板(通过传感器检测)
   ├── 调度系统检测到 MachineType=1, ProcessInfo.ID ≠ ""
   ├── TaskBordID 添加工件ID
   └── 找第一道工序的空闲设备 → 生成搬运任务

3. 天车搬运: 上料架 → 第一台加工机器
   ├── Z轴上升到顶 → 关接液盘
   ├── XY移动到源位置(上料架编码器位置)
   ├── Z轴下降到安全Z → 慢降到工作位
   ├── 充磁吸住工件
   ├── 上料架松开(如果是带夹具的料架)
   ├── 抖动松开工件
   ├── Z轴上升到安全Z → 到顶点
   ├── 关接液盘
   └── XY移动到目标机器

4. 天车向第一台机器放料
   ├── 开接液盘
   ├── 下发加工参数(外径/内径/长度/堵头厚度/斜度/打印/加工模式)
   ├── Z轴下降到工作位
   ├── XY偏移(上料偏移值)
   ├── 发"天车已靠近"+"天车上料到位"
   ├── 等机器夹紧(读104)
   ├── 退磁松开工件
   ├── Z轴上升到安全Z → 到顶点
   ├── 关接液盘
   └── 任务完成 → 天车恢复空闲

5. 机器加工
   ├── 机器: idle=0, 加工中
   ├── 加工完毕: over=1
   └── 调度系统检测到 → 加入 ListMachineOver

6. 搬运到下一道工序
   ├── 根据工件的 _WorkManShip[1] 确定下一道工序所需设备类型
   ├── FineIDLEMachine → 找空闲设备
   ├── 生成 CraneTaskInfo
   └── 重复步骤3-4

7. 最后一道工序 → 下料架
   ├── MachineType=2(下料架)
   ├── 天车放到下料架
   ├── 下料架检测到板
   ├── 删除任务(TaskBordID.Remove + TaskInfo.Remove + DeleteWorkInfo)
   └── 工件加工完毕，任务结束

```
## 七、关键判断条件汇总

### 调度层面的判断

| 条件 | 代码位置 | 含义 |
|------|------|------|
| `GetALLCraneGoHomeSta() == false` | ScheduledTasks入口 | 天车没回零 → 暂停 |
| `TaskPause == true` | 全局 | 手动模式 → 暂停调度 |
| `DataPoolLoadOver == false` | ScheduledTasks | 数据池未就绪 → 等待 |
| `err == 1` | 机器102 | 机器检修 → 跳过 |
| `Reservation == 1` | 机器120 | 已被预约 → 跳过 |
| `over == 1 && err == 0` | → MachineSta=1 | 需要下料 |
| `idle == 1 && over == 0` | → MachineSta=2 | 可以上料 |
| `!(天车startX <= 任务startX && 天车endX >= 任务endX)` | 天车分配 | 天车不可达 |
| 路权区间重叠 | 路权检测 | 任务冲突 → 移除 |
| 障碍物(其他天车在路径上) | 障碍检测 | 挡路天车让路 |

## 核心思想

**天车是唯一主动者，设备都是被动响应PLC信号。设备只做三件事：**
1. 发出状态（idle / over / 请求）
2. 接收数据（加工参数）
3. 执行夹紧 / 松开
```
