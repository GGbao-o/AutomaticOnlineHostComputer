# 全线业务逻辑核心文档重构设计

## 目标

将 `Docs/全线业务逻辑详解.md` 重构为整套系统唯一的核心业务流程文档。文档以当前源码行为为准，完整描述五台天车的调度、前置检查、动作步骤、状态转换、工件所有权、锁、异常收尾和人工恢复边界，同时说明机械手、货叉、双头镗、斜床、动平衡与研磨机如何构成天车的上下游条件。

## 内容边界

1. 五台天车是主线：1号线前天车、1号线后天车、2号线前天车、2号线后天车、研磨天车。
2. 机械手1、机械手2、机械手3、货叉、双头镗、打号机、斜床、动平衡和研磨机保留完整业务说明，但以它们与天车的交接和调度门槛为重点。
3. 正常业务、等待、异常、取消、人工结案、设备应急、内存复位和恢复启动全部纳入同一文档。
4. 文档只记录当前已经实现的行为。建议、风险和已知边界必须明确标为说明，不能写成系统已经执行的步骤。
5. 不修改任何业务代码、配置或设备协议，不创建 Git 提交。

## 组织方式

1. 先定义整线拓扑、五台天车职责和阅读规则。
2. 再定义所有流程共用的状态、工件所有权、动作账本、来源预约、锁、X11/X2、XYZ、超时和恢复原则。
3. 按工件流向依次描述任务入口、前端取料、货叉与双头镗、前天车、后天车上料、斜床加工、后天车下料、动平衡、研磨和最终出料。
4. 每个动作采用完全相同的说明模板：触发条件、锁外候选、锁内复核、状态写入、逐步动作、交接边界、成功收尾、异常收尾、人工恢复。
5. 最后集中说明跨流程碰撞区、连接管理、速度和运动参数、应急处理中心、内存复位、线路恢复与诊断顺序。

## 表达规则

1. 全篇不用 Markdown 表格。
2. 业务流程全部使用 `1.`、`2.`、`3.` 连续编号。
3. 状态机使用“状态名称 → 进入条件 → 允许动作 → 退出条件”的编号说明。
4. 地址、信号和配置只在对应动作中解释用途，避免脱离业务罗列点位。
5. 1、2号线相同逻辑先写共性，再逐项说明站号、架位、设备和信号差异。
6. 删除重复编号和按日期追加的孤立章节，把有效内容合并回其所属流程。

## 验证标准

1. 五台天车均能从文档中找到完整的取料、移动、放料、归位、异常和恢复步骤。
2. 每个会阻止派发的状态都能找到产生位置、判断位置和清理入口。
3. 明确区分普通 `Active` 来源预约与 `ManualResolution` 人工冻结。
4. 明确区分清空设备状态、恢复内存状态、来源结案、目标应急和线路 Resume。
5. 文档不存在 Markdown 表格、重复一级章节编号、占位词或与当前源码相反的表述。
