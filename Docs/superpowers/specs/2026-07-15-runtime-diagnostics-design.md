# 运行诊断页面设计说明

## 1. 目标

新增一个只读的“运行诊断”页面，帮助操作员直接看到：

- 1号线、2号线当前是否允许接收下一块板，以及首个阻止条件；
- 前后天车、斜床、研磨机是否存在需要人工确认的内存状态；
- 中转架物理有板信号与软件工件身份缓存是否一致；
- 关键设备当前连接状态和已有信号快照是否有效。

该页面只解释程序当前已经掌握的内存事实，不替代现场确认，不参与任何设备控制或流程判断。

## 2. 第一版范围

### 2.1 页面位置

主窗口导航顺序调整为：

`全流程状态 → 运行诊断 → 异常监控`

页面样式沿用项目现有卡片、颜色和表格样式，不引入新的第三方 UI 组件。

### 2.2 页面内容

页面分为三部分。

#### A. 概览卡片

显示以下数量：

- 前端可接板线路数；
- 通信断开项数；
- 信号快照无效或过期项数；
- 需要人工确认项数；
- 最近刷新时间。

这些数字只对本页面当前展示的诊断项做汇总，不作为自动流程的放行依据。

#### B. 当前等待原因

至少显示：

| 范围 | 状态 | 说明 |
|---|---|---|
| 1号线前端 | 可接板/等待 | 直接使用 `GetFrontDispatchReadiness()` 的现有只读结果 |
| 2号线前端 | 可接板/等待 | 直接使用 `GetFrontDispatchReadiness()` 的现有只读结果 |
| 1号线中转架 | 正常/不一致/数据不可用 | 对比既有物理信号快照和软件工件身份缓存 |
| 2号线中转架 | 正常/不一致/数据不可用 | 对比既有物理信号快照和软件工件身份缓存 |

前端“等待原因”严格复用已有准入判断结果，不在页面层重新实现一份业务判断，避免页面解释与真实调度条件产生偏差。

#### C. 人工确认与在途任务

显示：

- 五台天车当前任务；处于人工确认状态时突出显示确认说明；
- 十台斜床和四台研磨机中 `NeedsManualWorkpiece=true` 的工位；
- 中转架出现“物理有板但软件无身份”或“软件有身份但物理无板”的工位。

页面不提供“清除”“恢复”“继续”“重试”或设备移动按钮。需要处理时仍使用现有应急中心和手动操作入口。

## 3. 数据来源与隔离边界

第一版只使用以下已经存在的内存快照：

- `Line1FrontFlowEngine.GetFrontDispatchReadiness()`；
- `Line2FrontFlowEngine.GetFrontDispatchReadiness()`；
- 五台天车的 `GetCraneTaskSnapshot()`；
- 两条后端引擎的 `GetSkewStationSnapshots()`；
- 两条后端引擎的 `GetTransferRackSnapshots()`；
- `GrindingFlowEngine.GetGrinderStationSnapshots()`；
- 各引擎已经维护的 `DeviceStatus` 内存字段。

必须满足以下隔离要求：

1. 页面刷新不得调用任何 PLC、CNC、FANUC、Modbus、MC、文件共享或数据库接口；
2. 页面不得向引擎写字段，不得调用启动、暂停、清除、应急、移动、重连等方法；
3. 新增的快照聚合方法必须同步完成，只复制内存值，不执行 `await`、网络 I/O 或磁盘 I/O；
4. 快照只短暂获取现有的小粒度内存锁，复制后立即释放，不在锁内格式化 UI 文本；
5. 页面读取失败只显示“诊断快照暂不可用”，不得反向暂停或重启引擎。

## 4. 刷新与性能设计

- 页面使用 1 秒一次的 UI 定时刷新；
- 只有页面处于可见状态时启动定时器，切换到其他页面后立即停止；
- 每次刷新只复制少量快照，诊断项总量固定在几十条以内；
- 不新增后台常驻线程，不增加设备轮询频率；
- 不订阅高频设备事件，不为每个 PLC 周期创建诊断对象；
- ObservableCollection 只在 UI 线程更新，避免跨线程异常；
- 某一来源异常时单项降级，不影响其他诊断项显示。

因此，页面带来的开销仅是可见时每秒一次的小型内存复制和 UI 更新，不占用设备通信通道，也不进入自动线动作链路。

## 5. 组件设计

### 5.1 诊断快照模型

新增不可变的展示快照类型，包含：范围、项目、等级、当前状态、原因、更新时间。类型不持有设备客户端、引擎引用、锁或回调。

### 5.2 HomeViewModel 聚合入口

在 `HomeViewModel` 增加一个公开的只读聚合方法。它只访问已经初始化的引擎快照；引擎尚未初始化时返回明确的“未初始化”诊断项。

该方法不修改 `HomeViewModel` 的线路运行标志，也不触发 `OnPropertyChanged`，避免诊断读取影响主页面刷新链路。

### 5.3 RuntimeDiagnosticsViewModel

负责把聚合快照映射为概览数字和列表，提供 `Refresh()` 方法。它不直接持有或调用设备服务，只依赖单例 `HomeViewModel` 的只读聚合入口。

### 5.4 RuntimeDiagnosticsView

负责页面布局和可见性生命周期：

- 首次显示时立即刷新；
- 可见时每秒刷新；
- 隐藏或卸载时停止定时器；
- 页面关闭后不保留运行中的刷新任务。

## 6. 状态等级规则

第一版使用四类展示等级：

- 正常：已有内存证据表明当前项正常；
- 等待：业务条件暂未满足，但不是故障，例如双头镗未请求数据；
- 警告：通信断开、快照失效或物理/软件缓存不一致；
- 人工确认：天车任务或加工工位明确标记为需要人工核对。

“等待”不得显示为红色故障，避免操作员把正常节拍等待误认为报警。

## 7. 异常处理

- 单个快照源抛出异常：捕获后生成一条“诊断快照暂不可用”，不写日志风暴；
- 引擎未初始化：显示“未初始化”，不尝试创建引擎；
- 页面切换过程中刷新：通过 UI 定时器停止和可见性检查避免继续刷新；
- 程序关闭：不持久化诊断快照，不等待页面任务退出。

## 8. 文档更新

实现时同步更新：

- `Docs/整线技术手册.md`：增加“运行诊断页面”使用说明和只读边界；
- `Docs/日志审查与故障定位手册.md`：增加使用诊断页面定位等待、通信和人工确认问题的顺序；
- 本设计说明：记录第一版范围和不允许突破的性能/业务边界。

## 9. 验证标准

1. 项目完整构建成功，无新增警告和错误；
2. 导航中“运行诊断”位于“全流程状态”和“异常监控”之间；
3. 页面显示时能看到两条线前端准入原因、天车任务、人工确认项和中转架一致性；
4. 切换离开页面后，页面定时器停止；
5. 静态审查确认新增代码没有协议读写、数据库调用或业务控制命令；
6. 现有启动、暂停、分板、上料、下料、应急和手动移动代码路径不被修改；
7. 不提交 Git，由用户自行决定后续版本管理方式。

## 10. 明确不在第一版实现的内容

- 历史数据库、报警确认/关闭、操作员账号和权限；
- 新增设备心跳、连续失败计数或通讯耗时采集；
- 自动恢复、自动清状态、自动重连按钮；
- 修改任何现有准入规则、动作顺序、超时、轮询周期或握手逻辑；
- OEE、节拍统计、历史趋势和报表。

这些能力需要后续单独设计，不能借“诊断页面”名义进入当前自动流程。
