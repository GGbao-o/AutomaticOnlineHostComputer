# 1/2号线前端在途应急设计

## 1. 目标

为1号线、2号线前端新增独立的人工恢复入口，解决货叉、双头镗和机械手之间的软件在途状态在异常后无法继续、也无法安全作废的问题。

本功能只处理异常后的人工恢复，不改变正常自动流程的业务条件、寄存器地址、坐标、运动步骤、超时时间或状态转换顺序。

## 2. 当前问题

前端使用以下内存状态维持一块工件从总上料架到货叉、双头镗及前天车的进度：

- `_currentWp`：当前尚未交付给前天车队列的在途工件数据。
- `_forkPhase`：货叉与双头镗的业务阶段。
- `_manipulatorClearedFork`：机械手完成退磁放板、Z回零、到达本线安全Y并完成M801通知后才打开的货叉放行门闩。
- `_forkHandshakeInProgress`：防止同一握手子步骤重复执行的运行标志。
- `_boringUnloadDoneSent`：R6108是否已经写出的防重复标志。
- `_m912Sent`：M912送料命令是否已经写出的防重复标志。
- `_skipBoringTriggered`：跳过双头镗时M914及前天车派发是否已经触发。
- `_craneQueue`：已经到达Pos3、等待前天车取走的工件队列。

当板已经由机械手放到货叉，但机械手Z回零、安全Y移动或M801通知失败时，系统会保留 `_currentWp`，保持 `_forkPhase=Idle`，并让 `_manipulatorClearedFork=false`。引擎虽然暂停且软件锁最终释放，但恢复后货叉仍被门闩永久阻止，现有页面没有继续或作废入口。

主页“清空状态”只清双头镗的R6102、R6104、R6108，不修改上述内存状态。设备信号与软件阶段可能因此进一步失配。

## 3. 不在本次范围内

- 不重构现有前端状态机。
- 不增加自动超时或自动跳阶段。
- 不改变M900～M914、R6101～R6108的既有业务含义。
- 不自动移动机械手、货叉或前天车。
- 不在应急完成后自动恢复线体运行。
- 不清空 `_craneQueue`；该队列中的板已经交付给前天车流程，不属于 `_currentWp` 的作废范围。
- 不把普通“清空状态”改造成软件状态复位按钮。

## 4. 新增诊断信息

应急中心增加“前端在途应急”页签，可选择1号线或2号线并主动刷新。诊断必须显示：

1. 引擎是否运行、是否暂停。
2. `_currentWp` 是否存在及工件标识。
3. `_forkPhase` 当前阶段及中文含义。
4. `_manipulatorClearedFork`、`_forkHandshakeInProgress`、`_boringUnloadDoneSent`、`_m912Sent`、`_skipBoringTriggered`。
5. 机械手锁、货叉分派锁、前天车锁和中转架锁当前是否空闲。
6. `_craneQueue` 数量及队头工件；明确说明该队列不会被“丢弃当前工件”清除。
7. 货叉M900～M914实时状态，其中M903～M910为协议未使用位，但仍显示原始位值，便于排查PLC异常。
8. 双头镗R6101～R6108实时值，其中R6105、R6106当前没有业务定义，也必须显示原始值。
9. 机械手实时X、Y、Z及本线安全Y判断。
10. 读取失败时显示具体设备、异常类型和原因，不使用旧快照冒充实时值。

诊断只读，不修改任何业务状态。

## 5. 恢复动作一：板已在货叉，确认安全后继续

该动作只修复“板已经物理放在货叉，但放行门闩未打开”的确定性卡死，不允许跳过其他货叉或双头镗阶段。

### 5.1 前置条件

执行前必须全部满足：

1. 对应线体已经暂停；应急方法再次设置前端引擎暂停，防止页面状态与引擎状态短暂不一致。
2. `_currentWp != null`。
3. `_forkPhase == Idle`。
4. `_manipulatorClearedFork == false`。
5. `_forkHandshakeInProgress == false`。
6. 机械手锁、货叉分派锁、前天车锁均为空闲；说明旧动作已经退出关键区。
7. 实时读取货叉成功，且M900=1、M901=1、M902=0，即货叉在待机位并确认有板。
8. 实时读取机械手成功，且Z=0，Y等于本线配置的货叉释放安全Y，允许使用现有±10mm容差。
9. 操作员在弹窗中明确确认板已稳定放在货叉、机械手不持件且现场无人处于危险区。

任何条件不满足都拒绝操作，保持原内存状态和暂停状态。

### 5.2 执行顺序

1. 保持引擎暂停。
2. 重新读取并验证货叉和机械手实时状态，不复用页面显示快照。
3. 调用总上料架服务重新完成M801取料完成通知。
4. M801写入成功后，才设置 `_manipulatorClearedFork=true`。
5. 不修改 `_currentWp`、`_forkPhase` 和任何双头镗阶段标志。
6. 输出包含工件、现场读值和门闩变化的日志。
7. 保持线体暂停，由操作员检查诊断后使用原有启动/恢复按钮恢复运行。

如果M801写入失败，门闩不得打开。这与正常流程“先完成M801，再开门闩”的顺序完全一致。

## 6. 恢复动作二：丢弃当前工件并回Idle

该动作适用于操作员已经人工移走或决定报废当前在途板，目标是同时处理设备侧残留输出和上位机当前工件状态。

### 6.1 通用安全门槛

1. 对应线体必须暂停，并在方法入口再次设置暂停。
2. `_forkHandshakeInProgress` 必须为false。
3. 机械手锁、货叉分派锁和前天车锁必须为空闲。
4. 操作员必须确认机械手、货叉、双头镗和前天车均不在运动，磁铁和工件已人工处理到安全状态。
5. 仅处理 `_currentWp`；不清缓存FIFO、不清 `_craneQueue`、不释放其他流程当前持有的锁。

锁不空闲时不强行释放。应急功能不得把“锁当前被占用”误判成“锁残留”。

### 6.2 第一级：设备与软件一起清理

第一次执行时按以下顺序处理：

1. 清货叉上位机动作输出M911、M912、M913、M914，保留M900～M902等PLC输入位及其他未使用位。
2. 清双头镗上位机输出R6108、R6104、R6102，保持现场既定顺序；不写R6101、R6103、R6107等CNC输入。
3. 所有设备清零均成功后，在 `_wpLock` 保护下清空 `_currentWp`。
4. 设置 `_forkPhase=Idle`。
5. 清除 `_manipulatorClearedFork`、`_forkHandshakeInProgress`、`_boringUnloadDoneSent`、`_m912Sent`、`_skipBoringTriggered`。
6. 保持线体暂停，刷新诊断并提示“设备输出和软件当前工件状态已清；前天车队列未清”。

设备清零期间不得先清软件状态。若任意设备写入失败，软件状态保持不变，并返回统一前缀 `设备侧清零失败:`。

### 6.3 第二级：仅清软件

设备清零失败后，应急中心弹出第二次醒目确认。只有操作员确认已经通过PLC、设备面板或其他现场方式处理残留输出后，才调用 `skipDeviceClear=true` 的软件清理。

软件清理仍须重新检查线体暂停、握手未执行和相关动作锁空闲。成功后执行与第一级第3～6步相同的软件状态复位。

该分支日志和结果必须明确写出“仅清软件，设备信号未由本次操作确认清除”。

## 7. 普通双头镗清零保护

主页“清空状态”窗口保留原来的设备寄存器写入范围，但增加以下保护：

1. 点击1号线或2号线双头镗时，先向对应前端引擎查询是否存在在途状态。
2. 以下任一条件成立时禁止普通清零：`_currentWp != null`、`_forkPhase != Idle`、`_forkHandshakeInProgress == true`、任一阶段防重复标志仍为true。
3. 禁止弹窗必须显示当前工件和阶段，并指引操作员使用“应急处理中心→前端在途应急”。
4. 没有在途状态时仍显示明确警告：该按钮只清R6102/R6104/R6108，不恢复软件阶段，不处理工件、缓存、锁或设备运动。
5. 普通清零不检查或清理 `_craneQueue`，因为队列工件已经离开双头镗握手阶段。

## 8. 并发与失败语义

- 应急按钮自身防止重复点击。
- 引擎公开应急方法内部也使用独立的应急互斥，防止两个窗口或快速重复操作并发执行。
- 诊断与恢复读取实时设备状态时使用有界取消令牌，页面关闭或超时时返回失败，不改变软件状态。
- 所有异常均转为书面化结果并记录日志；不得在 `catch` 或 `finally` 中无条件改为Idle。
- `finally` 只释放应急方法自己取得的应急互斥，不执行设备写入、工件清空或阶段复位。

## 10. 验收标准

1. 正常运行时不调用新增应急方法，原状态机代码路径和状态转换保持不变。
2. 线体未暂停、握手仍在执行或锁仍被占用时，两个恢复动作均拒绝修改状态。
3. “继续当前板”只有在实时确认M900=1、M901=1、M902=0、机械手Z=0、本线安全Y且M801成功后才打开门闩。
4. 设备清零失败时 `_currentWp`、`_forkPhase` 和所有门闩保持原值。
5. 二次确认“仅清软件”成功后回Idle，但结果明确提示设备信号未确认。
6. 丢弃当前工件不改变缓存FIFO和前天车队列。
7. 普通双头镗清零在存在在途状态时被禁止。
8. 1号线和2号线行为对称，仅设备实例和安全Y不同。
9. 项目编译0错误，新增代码通过静态搜索确认没有修改正常业务地址、坐标、超时和既有阶段赋值。
