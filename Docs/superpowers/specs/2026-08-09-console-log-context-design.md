# 控制台日志动作上下文与中文化设计

**日期：** 2026-08-09  
**状态：** 已由用户确认，待实施

## 目标

为自动流程和人工操作的控制台日志补齐可追踪的动作上下文，并把面向操作员的字段改为中文可读表达。现场人员应能从单行日志识别：发生在哪条产线/引擎、哪台设备、哪一趟动作、哪块工件、哪个工位、正在做什么以及结果或等待原因。

## 不在范围内（硬约束）

本改造是日志旁路能力，**不得修改**以下任何业务行为：

- PLC 命令、读写顺序、等待时长、轮询频率、超时或重试；
- 锁的获取/释放、工件缓存、状态机转移；
- 异常抛出、异常处理、引擎暂停、自动回队或人工恢复路径；
- 运动、微调、设备安全保护的实际判定。

日志写入或格式化本身失败时必须静默降级到原 Console，不能向业务线程抛出异常。

## 统一显示格式

新建的高价值日志按下面格式输出：

```text
[级别][归属][设备][动作=动作号][事件]
中文结论 | 中文字段名=值；中文字段名=值
```

- **级别：** 信息、警告、错误。
- **归属：** 1号线前/后天车、2号线前/后天车、动平衡、研磨、人工操作等。
- **设备：** 具体天车、机械手、研磨机或“流程引擎”。
- **动作号：** 每一趟自动动作或一次人工操作生成一个唯一短编号；该动作下游日志继承同一编号。
- **事件：** 使用中文动作节点，例如“取料开始”“移动命令已发送”“到位确认”“等待PLC放料许可”“绝对值微调失败”“引擎暂停”。
- **字段：** PLC 位号、寄存器号和英文枚举可保留，但必须写中文含义，例如 `M720放料允许=0（暂不允许）`、`绝对编码器X=-2039`、`响应状态=未知（命令已发送，未完成确认）`。

每行仅在信息已知时追加板号、序号、来源/目标工位等字段；不伪造或猜测未知数据。

## 文件路由与兼容性

文件归属与显示格式完全解耦。

1. 先用现有 `EngineLogRouter` 的引擎作用域选择 `line1`、`line2`、`balance`、`grinding` 或 `shared` 文件。
2. 再把当前动作的显示上下文格式化到日志正文。
3. 保留目前按旧前缀（如 `[Line2Front]`）识别文件归属的兼容回退。
4. 新的 `[信息][2号线前天车]...` 标签不能参与或覆盖文件路由；没有已知归属的人工日志仍写入 `shared.log`。

因此，日志格式调整不能造成“2号线日志落入 shared.log”或根据设备名称猜测产线的错误。

## 上下文生命周期

新增一个仅存放诊断信息的异步日志上下文，作用域为单次动作：

1. 自动流程在一趟搬运/加工动作的入口创建动作号和已知的归属、设备、工件、工位。
2. 该上下文通过异步调用链传递给天车服务、微调帮助类和等待日志。
3. `using/finally` 在动作结束、异常或取消时恢复上一层上下文。
4. 两趟并行动作拥有独立上下文；动作结束后下一趟不能继承板号、工位或动作号。

上下文只供文字格式化读取，不可作为任何业务判断、路由决策或状态来源。

## 首轮覆盖范围

- 四台天车的主要搬运动作：开始、命令发送、到位确认、工件交接、完成、失败；
- X/Y 绝对编码器微调：开始、稳定读数结论、调整命令、调整确认、失败；
- M2/M3 的 PLC 许可等待：首次等待、周期性仍在等、许可恢复；
- 研磨主流程的关键动作；
- 人工天车运动控制的请求、命令已发送和确认结果；
- 所有流程异常与引擎暂停的根因/后果拆分。

不逐条重写低价值状态轮询；正常原始采样降低为诊断信息。发生微调失败或通信失败时，错误日志仍携带必要的原始样本和寄存器值。

## 验证策略

1. 路由：1号线、2号线、动平衡、研磨和人工日志仍写入原目的文件；旧前缀回退保持有效。
2. 隔离：并行动作的动作号、工件和工位不互相污染；释放后不泄漏到下一趟动作。
3. 格式：关键字段带中文含义，动作号和事件均可见。
4. 非业务性：日志建立、格式化或写入失败不影响正常返回值、异常传播、暂停判断或文件回退。
5. 使用现有项目测试和构建验证，且不修改现有业务契约的预期结果。
