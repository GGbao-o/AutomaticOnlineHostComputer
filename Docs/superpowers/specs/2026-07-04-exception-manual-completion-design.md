# 全量异常、暂停、弹窗、锁释放与恢复手册补全设计

## 1. 目标

将 `Docs/异常Catch_弹窗_暂停_锁释放与恢复审查.md` 重写并补全为当前项目异常处理的唯一权威手册。文档必须以当前源码为准，覆盖生产流程、通信层、页面告警和应急处理中的全部有效异常场景，并能回答现场人员最关心的六个问题：哪里出错、谁捕获、是否暂停、是否弹窗、锁与工件数据如何处理、怎样安全恢复。

## 2. 范围

### 2.1 必须覆盖的业务模块

1. 主页面任务入口与总上料架全局派发。
2. 1/2号线前端主循环、机械手1、货叉、双头镗、前天车、打号机和中转架。
3. 1/2号线后端主循环、斜床轮询、后天车上料、斜床握手、后天车下料和四个分流目标。
4. 动平衡引擎中的M2、M3及对应缓存和位置锁。
5. 研磨引擎中的ST709取料、研磨机上料、研磨机下料、ST710放料、状态卡死保护和恢复工件标记。
6. 天车、机械手、三菱MC、Modbus、Syntec、FANUC通信服务中的超时、重连和最终失败传播。
7. 天车XYZ全零保护、共享机械手安全告警和页面弹窗去重。
8. 斜床、动平衡、研磨应急处理，以及主页“清空状态”与应急处理的区别。

### 2.2 不纳入逐条场景正文的内容

- 纯UI样式、数据库普通查询和与生产派发无关的配置校验，仅在其会暂停生产、弹窗或改变生产状态时纳入。
- 第三方生成代码内部的所有异常不逐条展开，只说明项目封装层如何接收和传播。

## 4. 单个异常场景的固定模板

每个业务异常使用下列字段，不因篇幅省略关键字段：

| 字段 | 内容要求 |
|---|---|
| 场景名称 | 使用设备、业务动作和失败点命名 |
| 正常步骤 | 说明异常发生前正在执行的业务步骤 |
| 触发条件 | 写明信号、状态、通信或物理条件 |
| 异常来源 | 写明可能抛异常的方法和异常类型 |
| 捕获位置 | 写明内层或外层catch及其方法 |
| 变量解释 | 解释该分支使用的每个状态变量及真假含义 |
| catch处理 | 按代码顺序说明状态、缓存、信号和告警变化 |
| finally处理 | 说明必然执行的清理、锁释放、物理动作和可能二次失败 |
| 工件位置 | 区分已确认位置、推定位置和未知位置 |
| 暂停范围 | 不暂停、单引擎、整条线或两条线 |
| 弹窗 | 标题、正文要点、级别和去重规则 |
| 锁与缓存 | 逐把锁、逐个工件字段说明保留或清除 |
| 恢复方式 | 自动恢复、点击启动、应急处理或人工补信号 |
| 禁止操作 | 说明盲目启动、清状态或重复写信号的风险 |
| 代码证据 | 文件、方法和当前行号 |

## 5. 变量解释要求

首次出现以及不同模块语义不同时必须解释，至少覆盖：

- `_paused`、`_currentWp`、`_forkPhase`、`_manipulatorClearedFork`、`_forkHandshakeInProgress`。
- `magnetOn`、`holdingWorkpiece`、`placedOnFork`、`placedOnRack`、`rackCacheNotified`。
- `bed.St`、`bed.Wp`、`SignalFresh`、`WpRecoveryNeeded`、`CompletionExported`。
- `LoadHandshakeState.PlacedOnBed`、`LoadDoneNotified`。
- `PendingWorkpiece`、研磨机状态、M2/M3来源缓存。
- `EmergencyActionLease`、`ActiveOperation`、动作版本和失效语义。
- 后天车锁、前天车锁、机械手锁、中转架锁、共享区锁及M817/M818/M821/M720位置锁。

变量解释必须说明它是“命令已经发出”“设备反馈已经确认”还是“软件推断”；不得把三者混为一谈。

## 6. finally专项要求

为所有生产相关`finally`建立清单，至少说明：

1. 所属方法和正常所有权来源。
2. 无论成功、异常还是取消是否都会进入。
3. 释放哪些锁或重置哪些并发标志。
4. 是否执行设备读写或物理运动。
5. 使用原动作令牌还是独立令牌。
6. finally自身失败是否会覆盖原异常。
7. 释放锁后物理设备是否一定已离开危险区。
8. 当前行为是否存在已知风险。

## 8. 写作规范

- 使用完整书面语，避免仅用“回退”“兜底”“卡住”等口语而不解释具体动作。
- 第一次出现的缩写、寄存器、状态和变量必须解释。
- 表格用于横向比较，复杂因果使用分段说明；不得为了缩短篇幅把多个不同物理阶段合并成一个模糊场景。
- 明确区分“当前已实现”“当前风险”“建议修改”。
- 弹窗只在源码确实调用告警事件或`MessageBox`时写“会弹窗”；普通catch不能推断为弹窗。
- 锁只在代码确实持有时写“释放”；不得按方法名猜测。

## 9. 验收标准

1. 目标文档包含上述15个一级主题。
2. 四个线体引擎、动平衡和研磨的所有业务catch/finally均能映射到正文或明确的汇总表。
3. 所有生产安全告警事件和主页面弹窗入口均有去向说明。
4. 其他异常文档中的场景均已合并、纠正或在差异表中说明。
5. 每个物理承诺点均区分：未取到、X11确认持件、已退磁放下、设备完成信号已确认、下游缓存已确认。
6. 文档无待定占位、内部矛盾和失效链接。
7. 运行脚本或检索统计，验证代码异常边界与文档索引的覆盖关系。

## 10. 实施边界

本任务只修改文档和审计记录，不修改生产代码、PLC地址、状态机、异常处理、弹窗或应急行为。文档中发现的缺陷统一列入“尚未修改的风险”，不得写成已修复。
