# 双头镗握手无限等待设计

## 目标

仅取消1号线和2号线双头镗等待 `R6101=1`、`R6103=1` 的120秒业务超时。信号未到时保持当前工件和货叉阶段，持续读取，不暂停引擎。

## 现状与问题

前端引擎通过 `WaitForBoringSignalAsync` 使用全局 `Grinding.HandshakeTimeoutMs`。默认120秒后抛出 `TimeoutException`，`PauseForkBoringHandshake` 随即暂停整个前端引擎。暂停分支位于主循环状态采集之前，因此双头镗页面也停止刷新。

等待任务还会每50ms单独读取一个R寄存器，与页面使用的完整状态快照竞争同一Modbus连接。页面快照异常目前没有记录具体原因。

## 设计

1. 双头镗上料状态机增加“等待R6103请求上料”阶段。
2. `R6101`、`R6103` 和已有的 `R6107` 一样，由500ms主循环读取同一份 `ReadAllSignalsAsync` 快照并判断。
3. `R6101/R6103` 未置位时只保持阶段并节流记录等待日志，不设置 `_paused`，也不清理在途工件。
4. `R6101=1` 后按原顺序写 R2041~R2048 和 `R6102=1`，成功后进入等待R6103阶段。
5. `R6103=1` 后按原顺序进入 `GoingToBoring` 并发送 `M912=1`。
6. 页面继续使用同一轮双头镗完整快照；快照读取失败时记录节流异常日志，便于区分信号未到和通信失败。

## 保留的保护

- Modbus单次连接和读写硬超时保留，设备断线或半开连接不能永久占用线程。
- 参数写入、`R6102/R6104/R6108`写入失败仍调用 `PauseForkBoringHandshake`，因为此时设备可能已处于中间物理状态。
- 机械手安全位、天车运动、斜床、研磨机和打号机的超时不作修改。
- 双头镗加工阶段等待 `R6107` 原本就没有业务超时，继续允许20分钟以上加工。

## 验证

1. 保持R6101或R6103为0超过120秒，前端引擎不得暂停，页面仍持续刷新。
2. 将R6101置1，应只写一次参数和R6102，然后等待R6103。
3. 将R6103置1，应进入M912送料阶段。
4. 双头镗断线时，单次读写应按现有通信超时退出并触发重连，不出现无限阻塞。
5. 1号线ST103与2号线ST402行为完全对称。
