# 1/2号线共享区域锁拆分与后天车动态调度设计草案

> 日期：2026-07-08
> 状态：设计草案，待现场确认后再实施
> 范围：1号线前天车/后天车、2号线前天车/后天车、打号机、中转架、斜床1(ST108/ST606)、后天车上料/下料调度
> 明确不包含：PLC地址修改、坐标公式修改、正常取放料动作顺序修改、异常清空/应急按钮实现修改

## 1. 背景问题

当前每条线主要依赖一把 `SharedAreaLock` 保护“打号机 + 中转架 + 斜床1附近共享区域”。这套做法安全，但粒度过粗。

典型问题：

1. 后天车从 ST108/ST606 下料时会获取 `SharedAreaLock`。
2. 前天车从货叉 Pos3 取板后，进入打号机和中转架流程前也需要 `SharedAreaLock`。
3. 因此后天车只要在斜床1区域下料，前天车连打号机也去不了。
4. 中转架板数增加后，前天车可能被迫等待中转架空位；但后天车又可能因为固定“下料优先”不及时清中转架，形成效率低下。

现在的问题不是“没有锁”，而是：

- 锁的区域含义不清；
- 持锁时间太长；
- 上料/下料优先级写死；
- 部分锁保护了并不一定互相碰撞的动作。

## 2. 设计目标

1. 把原来的大共享区锁拆成更明确的区域锁。
2. 保持物理安全优先，不为了效率取消必要互斥。
3. 明确所有流程的拿锁顺序，避免死锁。
4. 后天车不再固定下料优先，而是根据中转架压力、可下料斜床数量、可加工匹配关系动态选择。
5. 所有判断必须能在日志中解释，现场看到“为什么这轮上料/下料”。

## 3. 锁拆分方案

每条线各自维护一套区域锁。

| 锁 | 含义 | 保护对象 |
|---|---|---|
| `MarkerLock` | 打号机区域锁 | 1号线 ST107 / 2号线 ST502 打号机放料、等待、取回 |
| `TransferRackLock` | 中转架区域锁 | 1号线 ST105/ST101/ST106，2号线 ST016/ST017/ST018 |
| `Skew1Lock` | 斜床1区域锁 | 1号线 ST108，2号线 ST606 |
| `FrontCraneLock` | 前天车自身锁 | 前天车单任务串行 |
| `RearCraneLock` | 后天车自身锁 | 后天车单任务串行 |

`TransferRackLock` 可以继续使用当前前后端共享的 `_transferRackLock`。`MarkerLock` 和 `Skew1Lock` 是新增区域锁。

## 4. 统一拿锁顺序

为了避免死锁，所有流程必须遵守统一拿锁顺序。

基础顺序：

```text
MarkerLock → TransferRackLock → Skew1Lock
```

谁需要多把锁，就只能按这个顺序获取。释放可以按业务阶段提前释放，但不能出现反向获取，例如：

- 已持有 `TransferRackLock` 后再等待 `MarkerLock`；
- 已持有 `Skew1Lock` 后再等待 `TransferRackLock`；
- 前后天车采用不同顺序互等。

### 4.1 当前草案中的争议点

用户指出：如果前天车打号前必须同时拿到 `TransferRackLock`，而后天车斜床1下料又持有 `TransferRackLock`，那么前天车仍然不能开始打号。这不符合期望。

因此最终方案不能简单照搬“前天车打号前必须同时拿 MarkerLock + TransferRackLock”这一版。需要进一步区分：

- 前天车去打号机是否只需要 `MarkerLock`；
- 前天车打号完成、准备从打号机取回并去中转架时，是否才需要 `TransferRackLock`；
- 后天车斜床1下料是否真的需要 `TransferRackLock` 全程持有，还是只需要 `Skew1Lock`；
- 如果斜床1下料确实需要挡中转架区域，能否只在 X+1000 退避前后的关键窗口持有。

本文后续流程先记录用户提出的锁顺序版本，并把上述争议列为实施前必须确认项。

## 5. 前天车流程草案

现有业务顺序保持：

```text
货叉Pos3取板
  → Z升0
  → 打号机放板
  → 等B.txt
  → 打号机取回
  → Z回到当前源码设计的中间安全位置，不强制回0
  → 中转架放料
```

用户提出的锁策略：

1. 前天车从货叉 Pos3 取板。
2. 取完板，Z 升到 0。
3. 此时已经预检到中转架有空位。
4. 开始获取区域锁。
5. 需要先拿到 `MarkerLock` 和 `TransferRackLock`。
6. 去打号机，完成打号机放板、等待 B.txt、重新充磁取回。
7. 打号机取回后，Z 不强制回 0，保持当前源码的设计。
8. 这时还需要获取 `Skew1Lock`。
9. 去中转架放料。
10. 放料完成、Z回安全、后端缓存回调成功后释放锁。

### 5.1 需要继续确认的问题

用户已经指出：如果第5步要求同时拿到 `TransferRackLock`，则后天车斜床1下料持有 `TransferRackLock` 时，前天车仍无法进入打号机。这不是期望。

可选修正方向：

1. 前天车打号阶段只拿 `MarkerLock`，打号取回后再尝试拿 `TransferRackLock` 和 `Skew1Lock` 去中转架。
2. 前天车打号前仍拿 `TransferRackLock`，但后天车斜床1下料不持有 `TransferRackLock`。
3. 保留前天车打号前拿 `TransferRackLock`，但把后天车斜床1下料持有 `TransferRackLock` 的范围缩短到确实穿越中转架的窗口。

从效率角度，方案1最能解决“前天车不能开始打号”的问题；从保守安全角度，方案2/3需要现场确认斜床1下料与中转架/打号机的真实碰撞关系。

## 6. 后天车上料流程草案

后天车上料是“从中转架取板，送到某台斜床”。

用户提出的锁策略：

1. 后天车开始上料时，先获取 `MarkerLock`。
2. 再获取 `TransferRackLock`。
3. 去中转架取板。
4. 下降、充磁、X11确认、Z回升。
5. 如果目标不是斜床1：
   - 释放 `MarkerLock` 和 `TransferRackLock`；
   - 后续去普通斜床上料，按原业务步骤执行。
6. 如果目标是斜床1：
   - 获取 `Skew1Lock`；
   - 释放 `MarkerLock`；
   - 保持 `TransferRackLock` 和 `Skew1Lock`；
   - 与斜床1执行上料交互；
   - 交互完成后 Z 回 0；
   - 执行 X+1000 退避；
   - 释放 `TransferRackLock` 和 `Skew1Lock`。

这里的核心意图是：后天车从中转架取板时，前天车不能同时进入打号机/中转架；如果后天车去斜床1，还要保护斜床1区域。

## 7. 后天车斜床1下料流程草案

后天车从斜床1下料时，用户提出：

1. 获取 `TransferRackLock`。
2. 获取 `Skew1Lock`。
3. 从 ST108/ST606 下料取板。
4. 完成斜床下料握手。
5. X+1000 退避。
6. 释放 `TransferRackLock` 和 `Skew1Lock`。

该策略的保守含义是：斜床1下料期间，后天车可能占用或穿越中转架/斜床1相邻区域，因此锁住中转架和斜床1。

但这也正是当前需要继续确认的矛盾：如果斜床1下料全程持有 `TransferRackLock`，前天车打号前又需要 `TransferRackLock`，前天车仍会被挡在打号机外。这一点已经由用户指出，最终设计必须调整。

## 8. 后天车动态调度算法

改造前后天车主循环是固定下料优先。当前实现已经改为先生成候选，再按压力选择上料或下料。

### 8.1 下料候选

一台斜床成为下料候选，需要同时满足：

1. 斜床状态为 `WaitingUnload`；
2. `bed.Wp != null`，软件知道这块工件是谁；
3. 完工记录已经写入，或本轮写入成功；
4. 目标下料位置允许放料；
5. 斜床信号新鲜，不能使用旧信号；
6. 后天车当前没有执行其它任务。

### 8.2 上料候选

一个上料候选由“中转架工件 + 可加工斜床”组成，需要同时满足：

1. 中转架物理有板；
2. 中转架软件缓存存在；
3. 至少一台斜床空闲、已连接、信号新鲜、`RqData=1`；
4. 该斜床的 `maxWorkpieceLengthMm` 能加工这块板；
5. 后天车当前没有执行其它任务。

`可匹配板数` 指的是：中转架上既有物理板又有软件缓存，并且当前至少存在一台可加工它的空闲斜床的板数。

### 8.3 决策规则

每一轮调度按以下顺序判断：

```text
1. 没有下料候选：执行上料
2. 没有上料候选：执行下料
3. 中转架满3个，并且有上料候选：强制上料
4. 中转架可匹配板数 >= 2 且 下料候选少于高下料压力阈值：优先上料
5. 下料候选达到高下料压力阈值 且 中转架可匹配板数 <= 1：优先下料
6. 其他情况：默认下料优先
```

解释：

- 中转架满3个时，前天车无法继续放料，必须优先给中转架腾位置。
- 中转架有2个可匹配板且下料压力不高时，也优先上料，防止前端被堵。
- 多台斜床等待下料且中转架只有0~1个可匹配板时，优先清斜床；高下料压力阈值按有效斜床数量动态折算：有效斜床0~1台阈值1，2~3台阈值2，4~5台阈值3。
- 没有上料候选或没有下料候选时，直接执行另一类，避免空转。
- 默认下料优先用于保守处理，避免已加工完成的板长期压在斜床内。

## 9. 代码结构建议

为避免继续把 1/2 号线两个后端引擎写得越来越长，建议抽两个小模块。

### 9.1 `LineSharedAreaLocks`

职责：

- 保存 `MarkerLock`、`TransferRackLock`、`Skew1Lock`；
- 提供按固定顺序获取锁的 helper；
- 输出锁状态文本；
- 统一释放日志；
- 避免 1/2 号线复制锁顺序导致死锁。

### 9.2 `RearCraneDispatchPlanner`

职责：

- 输入斜床快照、中转架快照、工件缓存、运动配置；
- 生成上料候选和下料候选；
- 计算中转架物理板数、可匹配板数、可下料斜床数；
- 根据规则输出本轮执行 `Load` 或 `Unload`；
- 输出原因文本，例如：
  - `中转架满3个，强制上料`
  - `可匹配板数=2，优先上料`
  - `可下料斜床数=4且可匹配板数=1，优先下料`
  - `无上料候选，执行下料`

## 10. 实施前必须确认的问题

1. 前天车打号阶段是否可以只持有 `MarkerLock`，等打号取回后再拿 `TransferRackLock`？
2. 后天车斜床1下料是否必须全程持有 `TransferRackLock`？
3. 后天车斜床1下料时，前天车在打号机位置放板/等待/取回，现场物理上是否允许同时存在？
4. `Skew1Lock` 是只保护 ST108/ST606 上方，还是也代表斜床1到中转架之间的穿越区域？
5. 如果打号机锁和中转架锁拆开，打号机等待 B.txt 的1小时期间是否允许后天车清中转架？

## 11. 2号线机械手两段移动同步结果

当前配置已调整为：

```json
"manipulator1Line2SafeY": 2000,
"manipulator1PickupStandbyY": 1000
```

当前 Line2 代码行为：

1. 机械手1把板放到 2号线货叉；
2. Z 回 0；
3. Y 移动到 `GetManipulator1SafeYForLine(2)`，当前为 2000；
4. 写 M801；
5. 设置 `_manipulatorClearedFork = true`；
6. 保持`_manipulatorLock`不释放，调用`MoveManipulator1ToPickupStandbyAfterForkReleaseAsync`；
7. 机械手继续移动到 `manipulator1PickupStandbyY=1000`；
8. 第二段到位后，`ProcessManipulatorPickupAsync.finally`才释放机械手锁。

因此2号线已经和1号线一致：先到本线货叉释放安全点放行货叉，再保持共享机械手锁回取板待机点。若以后把`manipulator1Line2SafeY`改回1000，使它与`manipulator1PickupStandbyY`相同，第二段方法会记录“无需第二段移动”并直接返回。
