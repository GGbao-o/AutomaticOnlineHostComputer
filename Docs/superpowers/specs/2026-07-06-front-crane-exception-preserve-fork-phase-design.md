# 前天车/打号机异常保留货叉—双头镗状态设计

## 1. 背景与故障结论

1号线现场出现以下组合状态：双头镗已经给出 `R6107=1`，货叉在待机位且无板，上位机仍保存当前在途工件，但 `_forkPhase=Idle`，因此程序不会执行 `M913=1`。

根因是前天车任务与货叉—双头镗状态机并行运行。上一块工件在打号机等待 `B.txt` 超时后，前天车异常分支无条件把全局 `_forkPhase` 以及相关门闩复位；此时这些字段可能已经属于下一块工件。异常恢复覆盖了另一条并行业务链的状态，导致下一块工件永久卡住。

## 2. 目标

- 前天车或打号机异常时暂停对应线体并弹窗。
- 保留当前货叉—双头镗阶段和门闩，禁止前天车异常把它们改成 `Idle` 或清零。
- 中转架锁、共享区锁和前天车流程锁仍必须在 `finally` 中释放。
- 人工确认旧工件已经退磁、移走或处于明确位置，并将前天车升到安全位置后，可点击恢复；货叉状态机从原阶段继续。
- 1号线和2号线采取完全对称的处理。

## 3. 不在本次范围内

- 不修改正常货叉、双头镗、前天车和打号机的业务步骤。
- 不修改寄存器地址、坐标公式、运动顺序和超时时间。
- 不增加自动机械恢复动作。
- 不因打号异常自动重发 `M912`、`M913`、`M914`、`R6104` 或 `R6108`。
- 不改变操作员必须确认现场物理状态后才能恢复的原则。

## 4. 采用方案

采用“异常域隔离”方案：前天车任务只能管理自己的暂停、告警、工件提示和锁释放，不能修改货叉—双头镗状态机的全局阶段。

在两条线 `ProcessCraneFrontAsync` 的异常处理中，删除以下无条件赋值：

```text
_forkPhase = ForkBoringPhase.Idle
_boringUnloadDoneSent = false
_m912Sent = false
_skipBoringTriggered = false
```

上述字段继续仅由货叉—双头镗状态机自身的正常阶段转换管理。

## 5. 异常行为

### 5.1 工件已放到中转架但缓存确认失败

- 设置 `_paused=true`。
- 弹窗提示人工补充缓存并确认现场。
- 不把工件重新放回前天车队列。
- 保留当前货叉阶段和全部货叉握手门闩。
- 释放中转架锁、共享区锁和前天车流程锁。

### 5.2 前天车已充磁或工件位置不确定

- 设置 `_paused=true`。
- 弹窗提示人工确认前天车、打号机及工件位置。
- 保留当前货叉阶段和全部货叉握手门闩。
- 释放当前持有的中转架锁、共享区锁和前天车流程锁。
- 不自动移动天车；操作员人工退磁、处理工件并将天车升到安全位置。

### 5.3 前天车尚未充磁，工件仍确认在货叉 Pos3

- 保持现有行为：工件重新进入前天车队列等待重试。
- 保留货叉阶段和握手门闩。
- 锁正常释放。

## 6. 恢复行为

操作员完成现场确认后点击恢复：

- `Resume()`只清除暂停标志。
- 如果保存阶段为 `WaitingMachine` 且 `R6107=1`，主循环继续执行 `M913=1`。
- 如果保存阶段为其他货叉阶段，则继续该阶段原有判断，不额外跳步。
- 如果现场状态与保存阶段不一致，操作员不得直接恢复，应先处理设备和工件位置。

## 7. 日志与告警

前天车异常日志和弹窗增加以下信息：

- 当前保留的 `_forkPhase`。
- 明确说明“货叉—双头镗阶段未复位”。
- 明确说明相关锁已经或将由 `finally` 释放。
- 提示人工确认旧工件及前天车安全位置后再恢复。

## 8. 验证标准

1. 1号线和2号线代码中，前天车异常分支不再赋值 `_forkPhase=Idle`，也不清除三个货叉门闩。
2. 正常完成时的货叉阶段复位逻辑保持不变。
3. 异常时 `_paused=true`，安全告警仍然触发。
4. `_transferRackLock`、`SharedAreaLock` 和 `_craneFrontLock` 的 `finally` 释放逻辑保持存在。
5. 项目编译通过。
6. 代码审查确认未修改正常信号地址、运动坐标、业务步骤和超时时间。
