# 生产异常监控结构化升级设计

## 1. 目标

把现有“少数安全弹窗和应急操作的内存镜像”升级为生产异常观察系统，覆盖：

- 最终失败；
- 自动恢复；
- 命令或物理结果未知；
- 连续通信、轮询和重连失败；
- 阶段、握手和软件锁等待滞留；
- 既有红色安全异常、黄色警告和应急操作。

每条事件必须能回答：哪里出错、正在处理哪块工件、最后确认到了哪一步、设备物理状态有哪些证据、软件怎样处理、哪些锁已释放、是否暂停、自动恢复是否成功、操作员必须做什么和禁止做什么。

本设计只增加旁路观察、页面展示和用户主动导出，不改变任何生产业务逻辑。

## 2. 已批准约束

1. 页面纯只读，只允许查看、筛选、复制和导出。
2. 不提供已阅、确认、清除、恢复、暂停或设备控制。
3. 新补充的监控事件不新增 `MessageBox`，不调用 `Pause/Resume`，不改变现有弹窗。
4. 原有状态机、缓存、工件所有权、锁、重试、超时、信号和设备命令保持不变。
5. 允许在现有引擎的异常与等待路径增加失败隔离的监控调用。
6. 监控调用只使用调用点已经掌握的数据，不为补详情额外读取PLC、CNC、天车、机械手或数据库。
7. 不使用数据库；当前进程最多保留5000个聚合事件。
8. 支持用户主动导出CSV和TXT；第一版不引入Excel依赖、不生成原生XLSX。
9. 重复事件保留首次时间、最近时间、累计次数、首次证据和最新证据。
10. 监控层任何异常不得传播到业务调用方。

## 3. 当前问题

### 3.1 当前采集不是异常总线

现有 `AttentionEventCenter` 只接收主页面的少数安全回调、后天车黄色警告和应急结果。普通catch、自动恢复、通信连续失败和阶段滞留不会进入页面。

### 3.2 弹窗去重会连同事件一起丢弃

`HandleLineSafetyAlarm` 和 `HandleStandaloneSafetyAlarm` 在 `AttentionEventCenter.Record` 之前判断弹窗去重并直接返回。同一暂停周期的第二个最终安全异常既不弹窗，也不进入异常页面。

### 3.3 物理结果未知被误写成确定状态

多个动作使用以下模式：

```csharp
await device.MagnetOnAsync(ct);
magnetOn = true;
```

若调用在命令可能已发送后抛错，布尔值仍为false。现有大catch可能把它描述为“未充磁”并自动回源，但真实含义是“命令响应未知”。监控描述必须准确反映证据，不能改变原catch行为，也不能重复设备命令。

### 3.4 页面结构不足以承载详细证据

当前事件只有 `Kind/Scope/Source/Message/Result`，表格只显示时间、等级、来源、正文和结果。长文本难以扫描，也无法按设备、工位、动作阶段、工件或异常代码筛选。

### 3.5 页面刷新存在尾事件漏刷窗口

UI取完快照但 `_refreshQueued` 尚未清零时发生的新事件会被合并返回；如果之后没有下一条事件，最新事件不会立即显示。

## 4. 方案选择

采用强类型事件和独立 `OperationalEventReporter`。

未采用以下方案：

- 继续扩展单一文本正文：无法可靠筛选、聚合和导出；
- 分析 `Console.WriteLine`：依赖不稳定文本格式，容易漏报和误报；
- 在通信底层全局拦截异常：缺少工件、阶段和物理承诺点上下文。

## 5. 单向旁路架构

```text
既有业务catch/等待循环/安全回调
        │ 只传调用点已有数据；void；无业务返回值
        ▼
OperationalEventReporter
        │ 同步、轻量、内部异常隔离
        ▼
OperationalEventStore
        │ 线程安全聚合、最多5000项、不可变快照
        ├──────────────► 异常页面 + 导航新事件计数
        └──────────────► 用户主动CSV/TXT导出
```

禁止任何反向链路：

- 页面不得调用引擎、设备服务、缓存、锁或状态机；
- Reporter不得读取设备、数据库或文件；
- Store不得执行业务动作；
- Exporter只消费Store快照；
- Reporter、Store、ViewModel或Exporter失败均不得改变业务catch/finally的执行。

### 5.1 组件职责

#### `OperationalEventReporter`

- 接收立即事件、连续失败观察、恢复观察和阶段心跳；
- 校验并规范化字段；
- 计算异常代码和聚合指纹；
- 调用Store；
- 整个入口内部捕获所有异常；
- 不返回会被业务使用的结果。

调用点构造上下文时只允许复制已经取得的局部值、nullable值和枚举，不调用设备、服务、格式化器或其他可能抛异常的方法。异常链展开、文本格式化、字段规范化和默认值补齐全部放在Reporter入口内部完成并隔离失败。这样既保留简洁的 `Report(new OperationalEventContext { ... })` 调用形式，也不会把新的高风险计算放进原业务catch/finally。

建议接口：

```csharp
public interface IOperationalEventReporter
{
    void Report(OperationalEventContext context);
    void ObserveTransientFailure(OperationalFailureObservation observation);
    void ObserveRecovery(OperationalRecoveryObservation observation);
    void ObserveStage(OperationalStageObservation observation);
}
```

四个方法均为 `void`，均不得抛异常。

#### `OperationalEventStore`

- 使用短临界区维护聚合事件；
- 固定容量5000个聚合项；
- 提供按版本号排序的不可变快照；
- 维护总接收数、聚合数、淘汰数、上报失败数和最后失败时间；
- 不引用任何设备或业务服务。

#### `LegacyAttentionEventAdapter`

保留现有安全和应急调用形式，由兼容适配器映射为新的结构化事件，避免同时存在两套页面数据源。原 `AttentionEventCenter.Record` 可作为过渡入口委托给Reporter。

既有主页面暂停顺序保持不变；事件记录移到弹窗去重return之前，使后续安全事件可以记录，但不新增第二个弹窗。

#### `OperationalEventExporter`

- 只在用户点击导出时工作；
- 先取得不可变快照，再执行格式化和文件写入；
- 不依赖Reporter和业务引擎；
- 导出失败只更新页面状态提示。

## 6. 强类型事件模型

### 6.1 顶层字段

`OperationalEvent` 至少包含：

| 字段 | 含义 |
|---|---|
| `EventId` | 聚合事件唯一ID，例如 `EVT-20260720-00428` |
| `ActionId` | 关联业务动作ID；没有动作上下文时为空 |
| `EventCode` | 稳定代码，例如 `CRANE_MAGNET_ON_RESPONSE_UNKNOWN` |
| `Severity` | `Critical/Error/Warning/Information` |
| `Category` | 安全、最终失败、结果未知、自动恢复、通信、阶段滞留、微调、运动、磁铁、传感器、握手、应急等 |
| `FirstOccurredAt` | 首次发生时间 |
| `LastOccurredAt` | 最近发生时间 |
| `OccurrenceCount` | 聚合次数 |
| `Scope` | 1号线、2号线、动平衡、研磨、全局 |
| `Engine` | 前端、后端、动平衡、研磨或主页面 |
| `DeviceType/DeviceNo` | 天车、机械手、货叉、双头镗、斜床、研磨机、PLC等 |
| `Station` | ST工位或寄存器区域 |
| `ActionStage` | 当前具体动作阶段 |
| `Title` | 一行简洁标题 |
| `PhysicalConclusion` | 依据已有证据得出的物理结论 |
| `BusinessPaused` | 原业务是否已经暂停；Reporter不得修改 |
| `FirstEvidence/LatestEvidence` | 首次与最新证据快照 |

### 6.2 嵌套证据

#### `WorkpieceEvidence`

- 版号、序号、直径、长度；
- 来源、目标；
- 软件当前所有者；
- 最后确认物理位置；
- 工件信息来源及可信度。

#### `PositionEvidence`

- 显示X/Y/Z；
- AbsX/AbsY；
- 目标值、偏差、容差、最大允许修正；
- 稳定采样次数、微调尝试次数；
- 数据采集时间；
- 未取得数据时必须标记 `Unavailable`，不能填0冒充真实坐标。

#### `MotionAndMagnetEvidence`

- Z下降命令状态；
- Z是否可能仍在低位；
- 充磁和退磁命令状态；
- X11最后值、读取是否有效、尝试次数和读取时间；
- `NotSent/SentUnconfirmed/Acknowledged/Failed/NotApplicable` 等明确枚举；
- 不允许仅用局部 `magnetOn=false` 推导“确定未充磁”。

#### `BusinessStateEvidence`

- 状态机修改前后值；
- 缓存修改前后值；
- 工件所有权修改前后值；
- `holdingWorkpiece/placed/cacheNotified` 等物理承诺点；
- 如果调用点没有某项证据，标记不可用并说明原因，不额外读取设备。

#### `LockEvidence`

- 相关锁名称；
- 异常发生时是否已知持有；
- catch/finally后是否已知释放；
- 仍需人工确认的碰撞区域；
- 不根据锁名称推断物理设备已经离开危险区。

#### `RecoveryEvidence`

- 是否自动恢复；
- 每个恢复步骤、结果和失败原因；
- 恢复后复核了哪些证据；
- 原业务是否继续、等待或暂停；
- Reporter只记录既有结果，不执行恢复。

#### `OperatorGuidance`

- 必须执行的现场检查；
- 明确禁止的操作；
- 是否允许按原流程继续；
- 文案来自稳定事件目录与调用点证据，不能使用模糊的“自行处理”。

#### `ExceptionEvidence`

- 异常类型；
- `Message`；
- `InnerException`摘要链；
- 业务包装上下文；
- StackTrace；
- 导出和“复制完整详情”包含完整内容，列表不直接展示堆栈。

### 6.3 字段真实性规则

1. 已确认、推定、未知、不可用和不适用必须分开表示。
2. 不用0代表读取失败；坐标和传感器证据使用nullable值加证据状态。
3. “命令成功返回”不等于“X11确认持件”。
4. “退磁成功返回”与“目标位通知成功”分别记录。
5. “锁已释放”不等于设备已经退避。
6. “引擎暂停”不等于已发设备命令停止。
7. Reporter不为补字段重新读取现场。

## 7. 事件采集策略

### 7.1 立即记录

以下事件首次发生即记录：

- 物理结果未知；
- 命令可能已发送但响应未知；
- 最终重试耗尽；
- X11残留板、X11读取最终失败或X11连续无板；
- 退磁、Z回安全或碰撞区退避失败；
- 工件已持有、已放下、PLC通知或下游缓存未闭环；
- 微调最终失败；
- `PressureStopException`，包括后来自动恢复成功；
- 既有安全告警、黄色警告和应急操作。

自动恢复成功使用 `AutomaticRecovery` 类别，不新增弹窗、不暂停。

### 7.2 连续失败阈值

单次普通轮询、连接探测和自动重连失败先只进入Reporter内部计数，不立即创建列表项。默认满足任一条件后创建事件：

- 连续3次失败；
- 从首次失败起持续30秒。

后续失败更新同一聚合项。首次成功响应后生成一条恢复事件，并结束该连续失败周期。

### 7.3 阶段滞留阈值

阶段观察阈值独立于业务超时，只决定何时显示非阻断事件。Reporter通过 `ObserveStage` 接收既有阶段和动作ID，不修改阶段。

使用独立 `Config/operational_event_monitor_settings.json`，由监控层启动时读取一次。Reporter运行期不做文件I/O。缺失或无效配置使用以下保守默认值：

| 阶段 | 默认观察阈值 |
|---|---:|
| 软件锁、ZoneMT、ZoneTS、位置锁等待 | 60秒 |
| R6101请求数据、R6103请求上料 | 10分钟 |
| R6107加工完成/请求下料 | 90分钟 |
| 货叉或天车返回等待 | 5分钟 |
| 中转架满位等待 | 10分钟 |
| 打号机B文件等待 | 30分钟；原1小时业务超时保持不变 |
| 其他握手等待 | 有业务超时时取现有超时的50%，最低60秒；没有业务超时时默认10分钟；只提示一次滞留 |

滞留后阶段继续推进时生成恢复事件，记录总滞留时长。阈值不得取消等待、抛业务异常或改变业务超时。

### 7.4 首批重点接入范围

1. 22个XY微调调用点，尤其7个取料前盲区；
2. 前天车、后天车、研磨天车、机械手1、M2和M3的充磁/退磁/X11；
3. 50个 `PressureStopException` 捕获点；
4. 工件持有、放料、PLC通知和缓存回调闭环；
5. 前后端、动平衡、研磨主循环和设备重连连续失败；
6. R6101/R6103/R6107、货叉返回、区域锁和位置锁等待；
7. 现有安全、警告、应急记录入口。

## 8. 重复聚合

### 8.1 聚合指纹

```text
EventCode
+ Scope
+ Engine
+ DeviceType/DeviceNo
+ Station
+ ActionStage
+ WorkpieceIdentity（存在时）
+ PhysicalConclusionCode
+ Severity
```

默认聚合时间窗口为10分钟，可在监控配置中调整。

### 8.2 不允许合并

以下任一变化必须新建事件：

- 工件身份不同；
- 严重度升级或下降；
- 物理结论由“未发送”变为“结果未知”、由“未知”变为“确认持件”等；
- 动作ID不同且包含独立工件动作；
- 超过聚合时间窗口。

### 8.3 聚合保留内容

- 首次证据不覆盖；
- 最新证据随最近一次更新；
- 保留首次和最近发生时间；
- 累加次数；
- 导出同时包含首次与最新证据摘要；
- 页面默认按最近发生时间倒序。

达到5000个聚合项后淘汰最旧项，并增加容量淘汰计数。页面必须明确显示“最多保留5000条聚合事件”，不能把KPI解释为完整永久历史。

## 9. 页面设计

采用“左侧事件列表 + 右侧完整详情”的主从布局。

### 9.1 顶部

- 标题与“当前运行周期、最多5000条、无数据库”说明；
- KPI：安全/结果未知、最终失败、警告、自动恢复、阶段滞留；
- 监控自检：累计接收数、聚合数、容量淘汰数、上报失败数、最后失败时间；
- 导航菜单显示新事件数量，最多显示 `99+`。

导航数量只是“自上次进入异常页面以来新增或更新的聚合事件数”。进入页面时只重置UI计数，不修改事件，不表示已阅或已处理。

### 9.2 筛选

- 时间范围；
- 严重度；
- 类别；
- 线路和引擎；
- 设备类型和编号；
- 工位；
- 是否暂停；
- 是否自动恢复；
- 仅看重复；
- 工件、动作ID、事件ID和全文关键字。

### 9.3 左侧列表

每行只显示定位字段：

- 严重度和类别；
- 最近时间；
- 标题；
- 线路、设备和工位；
- 动作阶段；
- 工件身份；
- 累计次数；
- 原业务是否暂停或自动恢复。

### 9.4 右侧详情

按固定八组展示：

1. 线路、设备与阶段；
2. 工件与流向；
3. 坐标与微调证据；
4. Z、磁铁与X11；
5. 状态、缓存与物理承诺点；
6. 暂停、锁与自动恢复；
7. 必须操作和禁止操作；
8. 完整异常链。

顶部单独显示“物理安全结论”，并明确区分已确认和未知。

### 9.5 只读交互

允许：

- 选择事件；
- 筛选和搜索；
- 复制完整详情；
- 导出当前筛选结果或全部事件。

禁止：

- 已阅、处理、确认、删除；
- 清报警；
- 恢复或暂停引擎；
- 写PLC/CNC；
- 修改缓存、工件或状态机。

### 9.6 刷新正确性

Store每次变化增加版本号。ViewModel刷新完成后再次比较Store版本；如果刷新期间有新事件，必须重新排队刷新，直到UI版本追上Store版本，消除尾事件漏刷窗口。

## 10. 导出

### 10.1 格式

第一版支持：

- CSV：UTF-8 BOM，Excel可直接打开；一条聚合事件一行，结构化字段展开成独立列；
- TXT：按页面八组详情输出，适合现场转发、打印和归档。

不新增第三方Excel包，不生成原生XLSX。

### 10.2 范围

导出菜单提供：

- 导出当前筛选结果；
- 导出全部保留事件。

文件名示例：

```text
异常监控_当前筛选_20260720_153012.csv
异常监控_全部_20260720_153012.txt
```

### 10.3 安全与隔离

- 使用 `SaveFileDialog` 由用户选择路径；
- 先复制不可变快照，再在后台格式化和写文件；
- CSV正确转义逗号、双引号、换行和中文；
- 以 `= + - @` 开头的文本字段加安全前缀，防止Excel公式注入；
- 导出失败只在页面状态栏显示，不记录生产事件；
- 不自动导出、不后台持久化、不使用数据库。

## 11. 详细文案生成

建立稳定 `OperationalEventCatalog`：

- `EventCode` 对应标题、默认严重度、类别、必须操作模板和禁止操作模板；
- 调用点只传事实证据；
- Formatter按固定顺序生成页面摘要、复制文本和TXT；
- 异常原文保留，不用统一模板覆盖底层具体信息；
- 对物理未知统一使用“可能已执行但未取得确认”，禁止写成“未执行”；
- 对自动恢复写明每一步和复核结果，不能只写“已恢复”。

示例：

```text
1号线天车1在ST713执行Pos3取料时，首次充磁命令等待响应超时。
命令可能已被PLC接收，但上位机未取得成功响应；X11尚未有效读取，磁铁和工件状态未知。
最后确认检查点：Z下降调用已返回，Z可能仍在取料低位。
原业务处理：任务重新进入前天车队列，引擎未暂停，前天车锁已释放。
必须确认：磁铁是否带电、X11真实状态、工件是否仍在ST713、天车Z位置。
禁止操作：禁止仅依据软件变量magnetOn=false直接再次取料或清除工件身份。
```

## 12. 监控层错误处理

1. Reporter入口捕获字段规范化、异常链展开、文案生成、聚合和通知中的所有异常；调用点的上下文初始化只复制已有简单值，不执行可能抛异常的计算。
2. Store写入和快照使用独立短锁，不取得业务锁。
3. UI订阅异常不得传播回Reporter。
4. 上报失败增加自检计数，尽量保存最后失败时间和简短原因；自检计数失败本身继续吞掉。
5. Exporter异常只更新UI导出状态。
6. 配置加载失败使用内置默认监控阈值，不影响业务配置加载。
7. 监控层不得通过重试调用业务方法弥补缺失证据。

## 13. 测试与验证

### 13.1 Reporter和Store单元测试

- 单条立即事件；
- 并发上报；
- Reporter内部异常不向调用方传播；
- 聚合指纹；
- 不同工件不合并；
- 严重度或物理结论变化不合并；
- 10分钟窗口边界；
- 首次证据保留、最新证据更新；
- 5000项容量淘汰；
- 快照倒序和版本号；
- 连续3次/30秒通信阈值；
- 通信恢复和阶段恢复事件；
- 使用可注入时钟测试阈值，不真实等待。

### 13.2 文案和导出测试

- 未发送、已发送未确认、成功返回、X11确认的措辞不能互相混淆；
- CSV逗号、双引号、换行、中文、UTF-8 BOM和公式注入；
- TXT八组详情完整；
- 空集合和当前筛选无结果；
- 导出异常只返回UI状态。

### 13.3 页面测试

- 空页面；
- KPI和监控自检；
- 各组合筛选；
- 主从选择和事件更新后保持合理选择；
- 右侧八组详情；
- 新事件导航数量；
- Store在UI刷新期间更新时能够补刷；
- 复制详情和导出范围。

### 13.4 业务隔离复核

逐个业务文件检查差异：

- 原分支条件不变；
- 原赋值顺序和返回值不变；
- 原catch/finally结构和锁释放不变；
- 原设备命令、暂停、重试和超时不变；
- 新增内容只允许只读局部证据、动作ID和Reporter调用；
- 监控命名空间不得引用通信客户端和设备动作服务；
- 模拟事件验证不连接真实PLC、不执行运动。

最后执行完整构建和全部新增测试。

## 14. 实施顺序

1. 新增事件模型、Reporter、Store、事件目录和测试；
2. 用兼容适配器迁移现有安全、警告和应急事件；
3. 修复事件记录与弹窗去重顺序，只移动监控调用，不改变暂停和弹窗规则；
4. 接入7个微调盲区和其他15个微调调用点；
5. 接入充磁、退磁、X11、PressureStop和物理闭环异常；
6. 接入通信连续失败、恢复和阶段滞留观察；
7. 重构异常页面为主从布局，增加导航数量和刷新版本追赶；
8. 增加CSV/TXT导出；
9. 完成业务隔离差异审查、测试和构建验证。

## 15. 验收标准

1. 22个微调调用点最终失败均能进入页面，包含原始微调详细证据。
2. 首次充磁调用抛错显示“结果未知”，不得显示“确定未充磁”。
3. X11残留板、退磁失败、PressureStop自动恢复、通信连续失败和阶段滞留均有对应事件。
4. 同一暂停周期的第二条安全异常能够记录，但不新增第二个弹窗。
5. 新增事件不改变任何暂停、恢复、重试、缓存、锁、状态机或设备命令。
6. 页面显示完整八组详情，支持全部批准筛选。
7. 最多5000个聚合项；聚合、不合并和容量规则符合本设计。
8. UI不会因刷新合并漏掉最后一条事件。
9. CSV可由Excel直接打开，TXT包含完整详情；两种导出均支持当前筛选和全部事件。
10. 不新增数据库、不自动持久化、不新增Excel依赖。
11. Reporter和UI失败不影响业务线程。
12. 完整构建和新增测试全部通过。

## 16. 明确不在本次范围

- 修改任何PLC、CNC、天车、机械手或料架协议；
- 修改业务暂停、恢复、重试和超时；
- 自动处理异常或自动执行恢复；
- 异常确认、已阅、处理人或工单；
- 数据库持久化；
- 自动后台日志归档；
- 原生XLSX、PDF或打印模板；
- 修改工件所有权和异常恢复业务缺陷本身。

监控页面会准确暴露这些业务缺陷，但本项目不借监控改造改变它们的处理结果。
