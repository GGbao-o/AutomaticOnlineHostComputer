# 总上料架全局分线准入与压力调度设计

## 1. 目标

总上料架的物理板由全局FIFO队头唯一对应。现有调度器在M800=1后主要依据板长能力、线路运行状态和粗略前端压力分配1/2号线，但不能区分“线路配置上能加工”和“线路此刻能够接板”。本设计只优化任务绑定1/2号线之前的准入判断，不改变机械手、货叉、双头镗、前天车、打号机、中转架及后端的正常动作步骤。

达到以下结果：

1. 当前物理板只分配给配置上能加工、且此刻具备前端接板条件的线路。
2. 一条线暂不可接时，另一条满足工艺和安全约束的线路可以接板。
3. 两条线都不可接时，工件继续保留在全局FIFO队头，页面显示每条线的具体等待原因。
4. 保留流水并行：前天车队列及正在执行的前天车任务只增加压力，不作为线路禁用条件。
5. 分线成功后仍由原线路引擎重新读取和复核设备条件；全局调度不代替动作安全检查。

## 2. 明确不改的业务边界

- 不改M800/M801复位门。
- 不改全局FIFO严格队头顺序，不跳过后续任务。
- 不改大直径强制1号线规则。
- 不改`skewBed.maxWorkpieceLengthMm`的板长能力判断。
- 不改R6101→写参数→R6102→等待R6103→M912的双头镗握手。
- R6103不作为全局分线条件，避免“未写数据所以CNC不请求上料、未请求上料所以不分线”的循环等待。
- 不改机械手共享锁、设备坐标、运动公式、超时时间、异常catch/finally和应急动作。
- 分线完成后不自动改派；线路前端缓存已经接管的任务仍由原线路处理。

## 3. 方案选择

### 3.1 未采用：只增加R6101判断

改动最小，但无法识别货叉有板、货叉不在待机位、`_forkPhase`未闭环或当前工件仍在前端的问题，仍可能把任务提前绑定到堵塞线路。

### 3.2 采用：准入快照加压力调度

每条线路引擎负责采集自身内存状态和既有设备快照，通过统一评估器生成只读的准入结果。全局调度器只消费结果，不直接连接或读取PLC。该方案隔离职责、改动可控，并保留原有动作前实时复核。

### 3.3 未采用：分线与机械手取板事务式预约

将任务绑定延迟到机械手真正取得动作锁以后最严格，但会把全局FIFO、共享机械手锁、M800和两条线路状态机耦合在一起，改动面和并发风险明显更大，不符合本次“只优化分线准入”的边界。

## 4. 封装结构

新增独立文件：

`Service/FlowEngine/FrontDispatchReadiness.cs`

其中包含三个小型类型：

```csharp
public sealed record FrontDispatchReadinessSnapshot(
    int Line,
    bool CanAccept,
    string RejectReason,
    int Pressure,
    DateTime CapturedAtUtc);

internal readonly record struct FrontDispatchReadinessInput(
    int Line,
    bool IsRunning,
    bool IsPaused,
    bool HasCurrentWorkpiece,
    bool ForkPhaseIdle,
    int CachedCount,
    bool ForkSnapshotValid,
    DateTime ForkSnapshotAtUtc,
    bool ForkAtStandby,
    bool ForkHasPlate,
    bool BoringSnapshotValid,
    DateTime BoringSnapshotAtUtc,
    bool BoringRequestData,
    int CraneQueueCount,
    bool FrontCraneActive);

internal static class FrontDispatchReadinessEvaluator
{
    internal static FrontDispatchReadinessSnapshot Evaluate(
        FrontDispatchReadinessInput input,
        DateTime nowUtc,
        TimeSpan maxSnapshotAge);
}
```

两个线路引擎各自只新增一个很薄的公开方法：

```csharp
public FrontDispatchReadinessSnapshot GetFrontDispatchReadiness();
```

方法只负责在本线路内部读取私有字段、组装`FrontDispatchReadinessInput`并调用共享评估器。所有条件顺序、拒绝原因和压力公式只在评估器中实现一次，避免1/2号线复制后发生行为漂移。

`HomeViewModel`只调用两个引擎的`GetFrontDispatchReadiness()`，不接触`_currentWp`、`_forkPhase`、货叉服务或双头镗服务等内部细节。

## 5. 快照字段与新鲜度

现有`DeviceStatus`已经保存双头镗R6101及`BoringSnapshotValid`，货叉则保存连接、有板和位置。为了禁止旧数据参与分线，两条线路的`DeviceStatus`补充：

- `ForkSnapshotValid`：本轮货叉状态是否读取成功；
- `ForkSnapshotAtUtc`：最后一次货叉成功读取的UTC时间；
- `ForkAtStandby`：最后一次成功读取时是否位于待机位；
- `BoringSnapshotAtUtc`：最后一次双头镗快照成功读取的UTC时间。

设备读取成功时同时更新值、有效标志和时间；读取失败时立即把对应有效标志置false，不用旧值冒充实时状态。

准入评估使用固定最大年龄3秒。线路主循环正常周期约500毫秒，继续负责货叉、双头镗等设备握手和状态刷新，不因本次分线优化而减速。全局分线调度器只消费这些内存快照，并以固定1秒周期读取M800、检查FIFO队头和重新评估线路准入。3秒新鲜度上限可以覆盖一次全局调度周期及短暂线程抖动；超过3秒仍未成功刷新时保守判定暂不可接板。准入判断本身只读取内存，不新增PLC通信。

## 6. 线路硬性准入条件

条件按以下顺序评估，第一项不满足即返回明确原因：

1. 线路引擎正在运行；
2. 线路未暂停；暂停也覆盖正在进行或尚未处理完成的前端应急情景；
3. 本线路前端缓存`CachedCount==0`；
4. `_currentWp==null`；1/2号线各自拥有独立的当前工件；
5. `_forkPhase==Idle`；即上一块板已经离开货叉Pos3，货叉回待机且无板，原握手阶段闭环；
6. 货叉快照有效且未超时；
7. 货叉位于待机位；
8. 货叉无板；
9. 双头镗快照有效且未超时；
10. R6101请求数据等于1。

`_craneQueue`和正在执行的前天车任务不属于硬性条件。它们代表前一块板已进入前天车/打号/中转架通道，允许线路前端继续流水，但必须计入压力以优先选择更空闲的线路。

全局调度器现有“任一线路前端缓存尚未消化就不派下一块”保护继续保留。它与M800复位门共同防止同一物理板或尚未被线路接管的物理板被重复派发。

## 7. 压力计算

统一公式：

```text
Pressure = CachedCount
         + (_currentWp存在 ? 1 : 0)
         + _craneQueue.Count
         + (前天车正在处理工件 ? 1 : 0)
```

为了统计已经从`_craneQueue`出队、但仍在Pos3取料、打号或放中转架的任务，两条前端引擎各增加一个线程安全的`_frontCraneActive`整数标志：

- 即将调用`ProcessCraneFrontAsync`前通过`Interlocked.Exchange(..., 1)`设置；
- 单工件调用使用专用`try/finally`，在finally通过`Interlocked.Exchange(..., 0)`清除；
- 只参与只读压力和诊断，不改变前天车锁、运动步骤或异常处理。

压力用于两个已经通过硬性准入的候选线路之间比较，不把压力大于某个值直接解释为不可接板。

## 8. 分线算法

全局分线循环统一定义命名周期`FrontDispatchPollInterval = 1秒`。所有“当前尚不能派发、下一轮重试”的正常等待分支均使用该周期，不再在同一循环内散落300毫秒、500毫秒和800毫秒延时。设备通信超时、动作超时和线路前端引擎周期不属于该常量的控制范围，保持原值。

因此，从M800或线路准入条件发生变化到调度器识别变化，正常最坏延迟小于等于约1秒。总上料架是一板一板进入、后续机械动作以秒级计时，该延迟不会降低实际生产节拍，却可以减少无意义的重复读取、状态计算和日志更新。

1. 全局FIFO为空：继续等待，不访问线路设备。
2. 正在等待上一块M800复位：保持现有复位门，必须亲自观察到M800=0。
3. 当前任务行未启动/已暂停：保持队头等待。
4. M800=0：任务显示“等待总上料架M800=1（物理板到位）”。
5. M800=1：先根据板长确定1/2号线理论加工能力。
6. 大直径达到强制阈值：只保留1号线理论候选；1号线准入失败则等待，不允许改派2号线。
7. 板长只有一条线能加工：仅检查该线准入；失败则等待。
8. 两条线都能加工：分别获取准入快照，过滤`CanAccept=false`线路。
9. 只有一条通过：分配给该线。
10. 两条都通过：选择`Pressure`较小者。
11. 压力相同：使用`_lastFrontDispatchLine`交替选择，不再固定偏向1号线；成功入线路缓存后才更新该值。
12. 两条都未通过：不从全局FIFO出队，显示两条线各自拒绝原因。
13. 选定线路后沿用现有出队、设置`AssignedLine`、调用`EnqueueWorkpiece`和失败回全局队头逻辑。
14. 成功后进入现有M800复位门。

## 9. 页面任务状态

沿用`TaskRowViewModel.Step`、`State`和`AssignedLineText`，不新增表格列、不修改XAML布局。

| 情景 | State | Step | AssignedLineText |
|---|---|---|---|
| 任务已启动但M800=0 | 等待中 | 等待总上料架M800=1（物理板到位） | 未分配 |
| M800=1且两线均不可接 | 等待中 | 物理板已到位，等待可接线路：1号线=原因；2号线=原因 | 未分配 |
| 强制1号线但1号线不可接 | 等待中 | 大直径必须走1号线，等待1号线可接板：原因 | 未分配 |
| 只有一条线具备板长能力但未就绪 | 等待中 | 等待可加工线路：具体原因 | 未分配 |
| 成功分配 | 运行中 | 已派发N号线前端缓存 | N号线 |
| 等上一块M800清零 | 等待中 | 等待上一块M800复位 | 未分配 |

任务进度仍通过`WorkpieceCache.ReportStage`旁路回调更新；更新失败只写日志，不参与调度结果。循环重复得到相同原因时允许属性层自行忽略相同值，生产日志沿用既有节流规则，避免每秒重复刷屏。

## 10. 并发与失败处理

- `GetFrontDispatchReadiness()`不得执行网络I/O、等待锁或设备动作。
- M800及总上料架状态由全局分线循环按1秒周期读取；线路货叉、双头镗快照继续由各线路引擎按原周期刷新。两类循环职责分离，不互相修改周期。
- `_currentWp`在既有`_wpLock`下读取；缓存数量沿用`_cacheLock`；`_craneQueue.Count`来自线程安全队列；活动标志使用`Volatile.Read`。
- 准入方法不得取得机械手锁、货叉分派锁或前天车锁，避免全局调度和线路动作形成新锁顺序。
- 快照无效、过期、引擎引用为空或状态不一致时统一返回`CanAccept=false`，不抛出导致全局循环退出的异常。
- 全局调度在真正调用`EnqueueWorkpiece`前可再次取得一次准入快照。若已变化为不可接，则任务仍留在全局FIFO；该二次检查只读内存。
- 分线与线路真正启动机械手之间仍有竞态窗口，因此原线路引擎对R6101、M800、货叉和机械手状态的实时检查必须完整保留。条件变化只会让任务在线路缓存等待，不会绕过安全条件执行动作。
- 不允许因为另一条线后来变空闲而自动搬移已经成功写入线路缓存的任务，避免软件任务顺序和总上料架物理板失配。

## 11. 代码规模控制

本次不重构两个前端引擎的既有两千余行流程。只抽取与本功能直接相关、能够纯函数化的准入判断：

- 共享类型和判断逻辑放入`FrontDispatchReadiness.cs`；
- 两条引擎只保留状态采集薄方法和快照字段更新；
- `HomeViewModel`只保留加工能力过滤、候选选择和任务状态上报；
- 不把PLC地址、设备服务或私有状态机枚举暴露给`HomeViewModel`。

这样既降低本次修改风险，也为后续逐步拆分大型引擎提供稳定边界，而不进行与当前需求无关的大规模重构。

## 12. 验证方案

### 12.1 静态与编译验证

- 两条线路均调用同一个`FrontDispatchReadinessEvaluator`，不得复制条件判断。
- 搜索确认全局调度未新增对`BoringModbusService`、`ForkService`或PLC客户端的直接调用。
- 搜索确认`ProcessManipulatorPickupAsync`、货叉状态机、R6101/R6103握手及M800复位门的原条件仍存在。
- 搜索确认`FrontDispatchLoopAsync`的正常重试统一使用命名的1秒调度周期，不再保留散落的300/500/800毫秒重试延时；设备动作和通信超时不得被误改。
- `git diff --check`无格式错误。
- 使用独立临时输出目录执行主项目完整`dotnet build`，要求0错误。

### 12.2 准入情景矩阵

至少逐项验证：

1. 1号可接、2号不可接：分1号。
2. 1号不可接、2号可接：分2号。
3. 两线可接且1号压力小：分1号。
4. 两线可接且2号压力小：分2号。
5. 两线压力相同：连续任务交替分配。
6. 两线R6101均为0：不出全局队头，显示两个原因。
7. R6101值为1但快照过期：不可接。
8. 货叉有板、非待机、断线或快照过期：对应线路不可接。
9. `_currentWp`非空或`_forkPhase`非Idle：对应线路不可接。
10. `_craneQueue`或前天车活动非空：线路仍可接，但压力增加。
11. 大直径强制1号线且1号未就绪：等待1号，不改派2号。
12. 仅一条线具备板长能力但未就绪：保持全局队头等待。
13. 分线入缓存抛异常：恢复`AssignedLine=0`并回全局队头。
14. 分线后线路条件变化：原机械手硬检查阻止动作，不发生盲取料。
15. M800持续为1：复位门阻止同一物理板再次派发。

### 12.3 现场验证边界

无PLC和机械设备环境只能验证编译、纯判断、日志和调用边界。现场应以空载或安全工件依次制造R6101未到、货叉有板、线路暂停、两线压力不同和M800不复位场景，确认页面原因、FIFO队头和实际分线一致。

## 13. 验收标准

- 全局调度只把当前板绑定到满足工艺能力和准入条件的线路。
- 不满足时任务仍在全局FIFO队头，`AssignedLine=0`。
- 页面能区分“等物理板”和“物理板已到、等线路”。
- 两条可接线路按完整压力选择，前天车任务被计入但不禁止流水。
- 平压交替，不固定偏向1号线。
- 全局分线循环每1秒重新读取M800并评估一次准入；1/2号线设备状态机仍保持原有刷新周期。
- 后续机械手及全部设备业务条件与修改前一致。
- 新增判断集中封装，1/2号线不出现两份独立准入算法。
