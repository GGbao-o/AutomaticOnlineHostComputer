# 设备IP修改、连接缓存与自动重连说明

> 核对日期：2026-10-17。依据当前工作区源码，仅更新文档；未连接现场设备、查询运行数据库或取得本次现场连接日志。

## 1. 先区分两个问题

**原目标地址断线后恢复连接，通常不需要重启程序。已经初始化的程序是否加载了数据库新IP，则取决于是否重新加载映射并重建相关服务。** 自动重连不等于自动读取数据库新IP，不能只用“开始连不上、后来连上”判断IP已经热切换。

当前生产源码中未找到`_driverRegistry`或`DriverRegistry`。本项目相关机制是`HomeViewModel`初始化、`CraneConnectionCache`、`ManipulatorConnectionCache`及各设备服务的连接/重连，不应将当前行为描述为“刷新了_driverRegistry”。

## 2. 修改数据库IP之后，实际执行什么

设备管理页面的编辑流程是：

```text
AddMachineDialog.Save_Click
    → ManagementUpdateService.UpdateMachineAsync
    → UPDATE machine，保存ip/port等字段
    → DialogResult=true，关闭对话框
    → MachineManagementView.LoadGridDataAsync
    → 重新查询设备列表并更新表格
```

这条流程没有调用生产主页强制重载，也没有通知天车/机械手连接缓存重新加载。重新查询得到的是新的行对象；不能据此认为引擎原来持有的行对象、服务对象或TCP连接已经替换。外部直接修改数据库同样没有在当前源码中接入生产IP自动变更通知。

切回主页面会触发`HomeViewModel.LoadAsync()`，默认`forceReload=false`。当`_enginesInitialized=true`时，提前进入`RefreshLoadedHomeAsync()`：只更新现有页面属性及卡片，不重新查询`machine`、不刷新设备IP映射、不重建引擎，也不重新连接设备。

因此，**“设备列表显示新IP”与“生产服务已经连接新IP”不能混为一谈**。线路普通暂停、重新点击启动，也不能当作数据库IP重新加载入口。

## 3. 哪些情况下会重新读取数据库IP

### 3.1 首次初始化

主页面尚未完成首次初始化时，`LoadAsync()`查询`machine`表，构造`IpMap`和工位缓存，再调用：

```text
_craneCache.LoadFromMachineRows(machineRows)
_manipulatorCache.LoadFromMachineRows(machineRows)
ManualControl.NotifyMappingsUpdated()
ForkManualControl.LoadMappings(machineRows)
```

后续创建各引擎、站卡及研磨机轮询服务。数据库修改若在这一轮查询前已提交，本次初始化可以取得新值，不需要先重启一次程序。

### 3.2 显式强制重载

代码保留`LoadAsync(forceReload: true)`，通过重建检查后会重新查询数据库并创建生产上下文。所以“技术上一定只能重启程序才能加载新IP”不是准确结论。

但当前调用检索中没有找到界面传入`true`的入口，不能把普通页面切换或设备列表刷新等同于这个能力。强制重载有以下约束：

- `IsAnyProductionEngineRunning()`为真时拒绝重建，普通暂停的后台引擎仍可能处于IsRunning状态。
- 前端、后端、全局待派发、动平衡、研磨等缓存未清空时拒绝重建。
- 还会读取部分现场料架握手信号，存在缓存/现场不一致或读取失败等原因时拒绝重建。
- 通过检查后先等待旧研磨采集循环退出，再停止状态同步并重建，避免旧循环继续注入旧连接。

没有执行上述重新加载时，程序保持已经装载的地址和服务。若需要加载数据库修改，应以实际重新初始化/受支持的重载流程为准；本次没有增加热切换按钮，也没有改变运行保护。

## 4. 各类设备如何保存和复用地址

| 设备/机制 | 地址来源与复用方式 | 普通重连会重新查数据库吗 |
|---|---|---|
| 5台天车 | 装载时按`TypeName=天车`及名称优先匹配，兼容旧库名称匹配；编号映射到服务实例 | 不会；服务内Modbus客户端保存创建时的IP |
| 机械手1/2/3 | 装载时按`TypeName=机械手`及名称匹配；各编号缓存服务实例 | 不会；连接缓存未重新装载时继续原目标 |
| 斜床 | 引擎持有工位行缓存，创建Modbus/FANUC服务；后台或动作侧重连复用服务/缓存地址 | 当前重连路径不查询`machine`表；不能把`TryIp`理解为实时查数据库 |
| 4台研磨机 | 启动采集循环时，从已加载工位缓存取得IP，并作为`GrinderPollLoopAsync`的参数传入 | 不会；重建PlcGrinderService仍使用本循环保存的ip参数 |
| MC连接缓存 | 按调用方传入的`IP:端口`缓存客户端；部分MC生产路径地址固定在源码中 | 不会；改变数据库不等于改变调用方传入的地址 |
| 打号机共享目录 | 前端引擎中的固定网络路径常量 | 不适用；修改数据库IP不会改共享路径 |

天车或机械手执行`LoadFromMachineRows`时，如果映射没变则保留共享连接；如果有变化，会更新映射，断开并清空该类设备缓存中的原服务，后续`GetOrCreateService`使用新映射创建服务。它不是直接把旧服务对象内部的IP改掉，也不是每次GetOrCreate都去数据库查询。

底层`ModbusTcpClient`的`_ip`和`_port`是readonly字段，构造时赋值；`ConnectAsync`重新连接的仍是这两个字段。仅断开再连接一个原有客户端，不会让它自动识别数据库新IP。

## 5. 为什么会出现“开始连不上，后来连上”

当前代码存在多个自动重连入口：

- 天车/机械手：`CraneService.SafeIoAsync`读取失败后可断开重连、延时再试；后续轮询也可能再次读取并连接。写操作的重试限制仍遵守原服务规则，不能扩大成所有物理命令都可以任意重放。
- 斜床：后端轮询会调度断线设备后台连接，FANUC存活Worker可自行退避重连，Modbus动作恢复也可尝试重连。
- 研磨机：`GrinderPollLoopAsync`首次或断连时重建服务并连接，失败后按原循环延时再试；动作阶段不允许替换时暂缓重建。

这些机制可以解释连接恢复，但不单独证明数据库热更新。具体场景应区分：

| 场景 | 可以解释的现象 | 不能据此推出 |
|---|---|---|
| 设备刚上电、网络未就绪、短暂掉线等恢复 | 原目标地址重试后成功，不需要重启上位机 | 程序已读取数据库新IP |
| 改的是PLC自身IP，使其与程序已加载目标一致 | PLC新地址生效后，原客户端重试可成功 | 数据库IP监听存在 |
| 数据库改完后才首次进入/完成初始化 | 初始化读取了新IP，之后连接成功 | 已运行的旧上下文会自动切换 |
| 已初始化后只改数据库，随后显示连接成功 | 还需核对实际目标地址、初始化记录和现场网络情况 | 仅凭时间先后认定是保存IP触发连接替换 |

没有设备名称、修改前后IP、修改的是数据库还是PLC自身，以及完整连接日志时，不能认定现场这一次属于上表哪种情景。

## 6. 从日志核对实际使用的IP

优先核对同一设备的创建、连接目标和成功记录，不只看卡片“已连接”颜色或设备表中的IP。例如源码可输出：

```text
[CraneCache] 新建服务：1号 ... <IP>
[CraneService] [...] 创建实例，IP=<IP>:<端口>
[ModbusTcpClient] 开始连接 <IP>:<端口>
[ModbusTcpClient] 连接成功 <IP>:<端口>
[GrinderPoll] [...] 首次连接 IP=<IP>...
[GrinderPoll] [...] 重连 IP=<IP>...
```

以上是便于检索的日志格式示意，不是现场采集记录；部分底层日志受日志开关控制。若同时出现主页首次初始化/强制重载日志及新映射，可继续追踪对应新服务是否真的连接成功。若只是原服务“正在连接/连接成功”，还要往前查其创建地址。

## 7. 与运动参数页修改IP的区别

研磨工件显示屏是单独的例子：配置页修改`grinding.workpieceDisplayIp`直接更新共享MotionConfig，`GrindingFlowEngine`在写显示屏时读取这个配置。后续显示屏写入可采用新地址。这不是`machine.ip`数据库编辑流程，也不能推导所有PLC设备地址都会如此即时生效。

运动参数页修改速度、X放行阈值等，同样需要按各参数读取时机理解；保存JSON不是重新查询数据库。参见[配置生效与XY微调核对](配置生效与XY微调核对.md)。
