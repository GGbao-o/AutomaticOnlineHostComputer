# 日志审查与故障定位手册

> 适用范围：当前 1/2 号线前后端引擎、货叉与双头镗、斜床、动平衡、研磨、天车、机械手、打标机及料架通信。  
> 编写依据：2026-06-28 当前源码中的 `Console.WriteLine`、工件缓存和状态机实现。源码变化后，本文关键词也应同步更新。

## 一、日志文件和使用原则

### 1. 日志位置

- 文件：`D:\BSH\1.txt`
- 程序同时向控制台和该文件输出。
- 文件采用追加模式，程序重启不会清空旧日志。
- `DualWriter` 每次写入后立即刷新，因此程序异常退出前已经输出的内容通常仍可在文件中找到。
- 每次启动会写入：

```text
启动时间：yyyy-MM-dd HH:mm:ss.fff
日志文件：D:\BSH\1.txt
```

审查故障时，应先找到故障前最近一次“启动时间”，避免把上一次运行的日志混入本次判断。

### 2. 三条基本原则

1. **先搜版号和序号，再看最后一条成功日志。** 最后一条成功日志通常就是工件停留位置。
2. **动作日志必须和物理现场核对。** “已发命令”不等于设备已经运动，“退磁完成”才表示软件认为工件已经放下。
3. **出现高危提示时不要直接恢复。** 先确认工件在哪、磁铁是否吸住、天车/机械手/货叉实际位置，再处理缓存和握手位。

### 3. 先用“运行诊断”缩小日志范围

主窗口“运行诊断”页面是日志排查前的只读入口。推荐顺序：

1. 先看1号线、2号线“前端准入”，确认当前首个拒绝原因；
2. 再看“通信断开”和“信号快照异常”，区分设备链路断开与业务条件等待；
3. 查看中转架物理有板信号和软件工件身份是否一致；
4. 查看五台天车任务和红色人工确认项；确实需要操作时再进入现有应急中心；
5. 页面缩小到具体线体、设备或工位后，再按本文关键词检索日志时间线。

注意：

- “等待”可能是正常节拍条件未满足，不应直接按故障清状态；
- 页面每1秒读取的是引擎已有内存快照，不是额外向PLC/CNC发起的实时读取；
- 页面不控制流程、不自动恢复、不清理工件缓存，也不替代现场物理确认；
- 页面用于查看当前事实，日志仍用于追溯先后顺序和异常发生前后的动作细节。

## 二、最常用的检索命令

以下命令可在 PowerShell 中直接使用。

### 1. 按版号和序号精确追踪

```powershell
rg -n -F "版号=ABC123 序号=01" "D:\BSH\1.txt"
```

查看匹配行前后各 10 行：

```powershell
rg -n -C 10 -F "版号=ABC123 序号=01" "D:\BSH\1.txt"
```

序号不确定时只搜版号：

```powershell
rg -n -F "版号=ABC123" "D:\BSH\1.txt"
```

只有序号时可以搜索：

```powershell
rg -n -F "序号=01" "D:\BSH\1.txt"
```

注意：序号可能在不同版号中重复，只搜序号不能唯一确定工件。

### 2. 实时查看最新日志

```powershell
Get-Content -Path "D:\BSH\1.txt" -Encoding UTF8 -Tail 100 -Wait
```

### 3. 搜索全部高风险信息

```powershell
rg -n -C 5 "⚠⚠⚠|❌|异常|失败|超时|已暂停|禁止|未闭环|未确认|已隔离" "D:\BSH\1.txt"
```

### 4. 搜索某条生产线

```powershell
rg -n "\[Line1Front\]|\[后引擎\]" "D:\BSH\1.txt"
rg -n "\[Line2Front\]|\[后引擎2\]" "D:\BSH\1.txt"
```

### 5. 搜索某类设备

```powershell
rg -n "\[CraneService\]|\[ForkSvc\]|\[BoringModbusSvc\]" "D:\BSH\1.txt"
rg -n "\[平衡引擎|\[GrindingEngine\]|\[GrinderSvc\]" "D:\BSH\1.txt"
```

如果电脑没有 `rg`，可使用：

```powershell
Select-String -Path "D:\BSH\1.txt" -SimpleMatch "版号=ABC123 序号=01" -Context 10,10
```

## 三、按版号/序号追踪一块板

工件统一标识由 `WorkpieceCache.IdentityText` 生成：

```text
版号=实际版号 序号=实际序号
```

如果软件没有拿到版号，则显示：

```text
版号=未知
```

### 1. 推荐审查步骤

1. 精确搜索 `版号=... 序号=...`。
2. 从第一条“入缓存”开始按行号向下阅读。
3. 找出该工件的最后一条成功日志。
4. 继续查看其后 20 至 50 行，寻找通信异常、条件不满足、等待锁或引擎暂停。
5. 同时搜索工件所在设备的服务前缀，例如 `[ForkSvc]`、`[CraneService]`。
6. 到现场确认工件物理位置与最后一条日志是否一致。

### 2. 正常工件链路关键词

一块板不一定经过所有环节，但正常日志大致按以下顺序出现：

```text
[ERP导入] / [FrontDispatch]
  → 入全局FIFO
  → 等待上一块M800复位 / 已观察到上一块M800复位为0
  → M800=1 ... → 1/2号线
  → [Line1Front] 或 [Line2Front] 入缓存
  → M800=1 缓存有料
  → [机械手1] 取料送叉
  → [货叉] R6104=1 上料完成
  → [货叉] R6107=1 加工完成
  → [货叉] R6108=1 下料完成
  → [天车调度] 出队
  → [前天车] 天车流程开始
  → [打号机] 完成
  → [中转架] 放料完成
  → [后引擎] 或 [后引擎2] 工件缓存写入
  → 斜床上料、加工、下料
  → ST019/ST020/ST021 或 ST010
  → [平衡引擎] M2/M3
  → [GrindingEngine] 工件入缓存
  → 研磨上料、加工、下料完成
```

`SkipBoring` 工件不会经过双头镗加工，正常关键日志是：

```text
SkipBoring
  → M914=1
  → Pos3已到位
  → 工件入天车队列
```

### 3. 如何判断工件停在哪一步

| 最后一条工件日志 | 优先检查 |
|---|---|
| `入全局FIFO`，之后没有线路入缓存 | 先搜同时间的`等待上一块M800复位`、`等M800=1`、`队头暂不能派发`和`派发循环异常` |
| `等待上一块M800复位: 当前M800=1` | 上一块已派发但调度器尚未读到M800=0；确认机械手是否取走、M801是否发送、PLC是否复位M800。FIFO为空仍出现该日志是正常安全观察 |
| `已观察到上一块M800复位为0` | 防重复派发门已解除；若仍不派发，继续检查新板M800=1和线路选取条件 |
| `等M800=1` | 调度器已就绪，但总上料架当前没有请求取料信号；对照页面M800和`CenteringRackSvc`原始字 |
| `队头暂不能派发` | 读取日志末尾的具体原因：线路未启动/暂停、版长能力、大直径强制1号线、货叉快照过期、货叉有板、货叉不在待机、`_currentWp`非空、`_forkPhase`未回Idle、R6101未请求数据等 |
| `物理板已到位，等待可接线路` | M800=1已经成立，板在总上料架取料位，但1/2号线前端准入均失败；直接看任务栏或日志中的“1号线=原因；2号线=原因” |
| `二次准入失败` | 选线后、真正写入线路缓存前状态变化；任务仍在全局FIFO队头，不是丢任务 |
| `入缓存`，之后没有 `M800=1` | 总上料架 M800、机械手1连接、货叉条件、引擎是否启动 |
| `M800=1 ... 启动机械手1` | 机械手锁、货叉待机/有板、机械手安全位置、X11 |
| `取料送叉完成` | 货叉/双头镗状态机、R6101/R6103、M912 |
| `R6104=1 上料完成` | 双头镗加工状态和 R6107 |
| `R6107=1 ... M913=1` | 货叉是否到 Pos3、M902、货叉有板 M900 |
| `R6108=1 ... 入天车队列` | 前天车连接、天车锁、目标中转架、打标机 |
| `天车流程开始`但无完成 | 天车是否吸住、打标交互、目标架缓存回调；重点搜 `⚠⚠⚠` |
| `中转架放料完成` | 对应后端缓存是否确认、后引擎是否启动 |
| `开始下料`但无完成 | 后天车、X11、目标料架允许位、缓存回调和完成位写入 |
| `[GrindingEngine] 工件入缓存` | 研磨机请求数据、分配条件、研磨天车锁 |
| `已放入研磨机但握手未完全闭环` | 工件已在设备内，必须现场确认后再恢复 |

### FrontDispatch等待原因速查（2026-07-07）

全局分线循环按1秒周期运行。若主页面任务栏显示“等待中”，优先看当前工序文字：

| 当前工序/日志原因 | 含义 | 现场优先检查 |
|---|---|---|
| `等待总上料架M800=1（物理板到位）` | 全局FIFO有队头任务，但总上料架当前未请求取料 | 总上料架是否已放板、M800原始位、D100 |
| `等待上一块M800复位` | 上一块已派发，调度器还未亲眼看到M800=0 | 机械手是否已取走上一块、M801是否脉冲成功、PLC是否复位M800 |
| `等待线路前端缓存消化` | 至少一条线路前端缓存尚未清空，当前代码保守不派下一块 | 1/2号线前端缓存数量、对应线是否启动、是否暂停 |
| `货叉快照无效或过期` | 该线最近3秒内没有成功读取货叉M900~M914 | 货叉MC连接、M900/M901/M902、线路前端主循环是否暂停 |
| `货叉不在待机位` | M901未满足，货叉可能在Pos2/Pos3/动作中 | 货叉现场位置、M911/M912/M913/M914命令残留 |
| `货叉仍有板` | M900=1，该线不能再接总上料架新板 | 是否上一块还在货叉待机位或Pos3未被天车取走 |
| `前段_currentWp仍有在途工件` | 机械手到货叉/双头镗/Pos3前段还没交给前天车队列 | 机械手送叉是否完成、门闩、货叉双头镗阶段 |
| `货叉/双头镗阶段未回Idle` | `_forkPhase`不是Idle，上一块货叉状态机未闭环 | R6101/R6103/R6107、M912/M913/M911、货叉是否回待机无板 |
| `双头镗快照无效或过期` | 最近3秒内没有成功读取R6101~R6108 | 双头镗Modbus连接、R区读取 |
| `双头镗R6101未请求数据` | 双头镗未请求数据，不能把新板派入该线前端 | 双头镗是否忙、报警、未回初始请求数据 |

注意：`R6103`不是分线条件。只有分线后写入加工参数并置`R6102=1`，CNC才可能请求上料`R6103=1`。分线前等待R6103会导致死等。

## 六、货叉与双头镗故障定位

### 1. 正常握手顺序

```text
R6101=1 请求数据
  → 写 R2041/R2043/R2044/R2045/R2047
  → R6102=1 数据下发完成
  → R6103=1 请求上料
  → M912=1 货叉送料
  → M901=1 且 M900=0 货叉回待机且无板
  → R6104=1 上料完成
  → R6107=1 请求下料
  → M913=1 货叉取料并去Pos3
  → M902=1 到Pos3
  → R6108=1 下料完成
  → 工件进入前天车队列
  → 前天车Pos3下降并由X11确认吸住
  → 前天车Z回升到安全高度 与 M911=1货叉回待机 并行
  → 两边完成后前天车继续打号
```

R6102、R6104分别在数据下发和上料完成时写`1`；本轮下料完成时按`R6108=1 → R6102=0 → R6104=0`立即清理，R6108保持为1。

### 2. 关键词判断

| 日志停留点 | 判断 |
|---|---|
| 等待 `R6101` | 双头镗未请求数据，或Modbus连接异常 |
| 已写参数但没有 `R6102=1` | 参数写入或数据完成位写入失败 |
| 等待 `R6103` | 双头镗未进入请求上料状态 |
| 已发 `M912=1`但没有回待机 | 货叉动作未完成；核对 M900/M901/M902 |
| 已写 `R6104=1`，长期无 `R6107=1` | 双头镗仍加工、设备报警或请求下料未读到 |
| 已发 `M913=1`但无 `M902=1` | 货叉未到Pos3或状态读取异常 |
| `Pos3已到位, 但双头镗Modbus未连接` | 板已在Pos3，但R6108无法写入；待连接恢复 |
| 已看到 `X11=1 已吸到`，但未看到 `Z升安全高度 与 M911货叉回待机 并行` | 运行版本不对，或X11确认后流程被取消/暂停 |
| 已看到并行启动日志，但只有Z回升或M911其中一侧完成 | 对应侧通信、到位反馈或写入异常；外层会按“工件已在天车上”暂停并保留现场 |
| `握手异常`、`保持阶段`、`引擎已暂停` | 状态机故意保留现场阶段，禁止按普通空闲重新派发 |

Pos3正常交接的关键日志顺序是：`X11=1 已吸到` → `Z升安全高度 与 M911货叉回待机 并行` → `并行通知货叉回待机位 M911=1`/Z回升日志交错出现 → `Z安全高度与货叉回待机命令均已完成`。M911日志允许出现在Z回升完成之前。

### 3. SkipBoring

SkipBoring 仍要求双头镗在线并且 `R6101=1`，用于避免设备节拍冲突。之后货叉执行：

```text
M914=1 → 货叉从待机位直接送到Pos3 → 工件进入天车队列
```

搜索：

```powershell

```

## 十二、日志节流后的正确解读

为降低磁盘IO和重复日志，部分高频状态只在“状态变化”或心跳周期到达时输出：

| 日志类型 | 当前规则 |
|---|---|
| 天车通用状态 | 关键状态变化立即输出；不变时约10秒心跳一次 |
| 货叉M900~M914原始状态 | 原始字变化立即输出；不变时约10秒心跳一次 |
| MC63料架M800~M831/D100 | 原始值变化立即输出；不变时约10秒心跳一次 |
| 全局调度M800复位门 | M800变0立即输出解除日志；持续为1时约3~5秒输出一次，包含D100、FIFO数量和下一任务 |
| 前端货叉状态机快照 | 阶段或关键状态变化立即输出；不变时约10秒心跳一次 |
| 研磨等待天车锁 | 同类等待约10秒输出一次 |
| 打标共享目录状态 | 连接变化立即输出；不变时约30秒心跳一次 |
| 前端慢轮告警 | 最多约10秒输出一次，避免故障时刷屏 |

因此：

- 两条相邻状态日志间没有每500ms记录，不代表中间没有读取。
- PLC位变化、动作命令、完成通知、暂停和异常仍应保留关键日志。
- 判断“读不到请求下料”时，不要仅凭缺少重复状态行；应同时查设备连接、状态变化日志、状态机阶段和后续动作日志。
- 主页面能显示M800不代表全局调度器已经解除复位门；必须同时搜索`[FrontDispatch]`的复位门日志。页面状态采集、线路前端采集和全局调度是不同消费者。
- 一批任务全部派发后FIFO可能为空，但调度器仍会短暂输出`等待上一块M800复位`，直到看到最后一块对应的M800=0；这是正常安全行为。

## 十三、高危日志处理清单

出现下列日志时，先暂停自动处理并核对现场：

| 高危关键词 | 必须确认 |
|---|---|
| `天车已充磁但流程中断` | 哪台天车、磁铁是否吸板、X/Y/Z位置、软件在途工件 |
| `已吸住工件但未放` | 哪台机械手、X11、工件目标位是否空闲 |
| `工件已在...但后端缓存未确认` | 板实际在哪个中转架、后端缓存是否已有同一版号序号 |
| `已放...但M711/M721未确认` | 板已放下，PLC完成位是否补写成功，禁止重复放板 |
| `已放入研磨机但握手未完全闭环` | 研磨机内是否有板、请求位和完成位、PendingWorkpiece |
| `已放到ST710但无法写M721` | ST710实物、MC64连接和M721实际值 |
| `通信Worker已隔离` | 对应CNC是否仍在线；通常需要重启上位机恢复该Worker |
| `旧动作已被应急取消` | 应急动作是否与当前物理状态一致，旧任务已不会继续写状态 |

不要只清PLC位或只清软件缓存。物理工件、PLC握手和软件缓存三者必须重新对齐。

## 十四、锁等待和疑似卡死判断

常见锁关键词：

```text
机械手锁
天车锁
ZoneMT
ZoneTS
共享区锁 / 中转架锁（旧日志或历史文档用语）
M817锁 / M818锁 / M821锁 / M720锁
```

判断方法：

1. 搜索锁名，找到最近一次“获取/已获取”。
2. 查看持锁动作是否有对应“完成/释放”。
3. 如果动作仍有状态变化或周期等待日志，通常是条件等待，不一定死锁。
4. 如果长时间没有动作、没有异常、也没有释放日志，再检查占锁任务是否停在设备IO。
5. 多把锁场景要同时检查第二把锁等待期间，第一把锁是否在异常或取消后释放。

## 十六、当前日志的边界

1. 日志文件中的每一行没有统一时间戳，只有部分业务日志自行带时间。排查时需借助启动时间、行号和上下文判断先后。
2. 文件为追加写入，同一个版号在不同启动批次可能重复出现。
3. 状态日志经过节流，不能用“没有每500ms输出”推断“程序没有读取”。
4. `ReportStage` 成功回调不一定写入日志文件；工件追踪应以各引擎带 `IdentityText` 的动作日志为主。
5. `版号=未知` 表示当前工件数据没有完整身份，必须结合站位、直径、长度和现场确认，不能仅靠该关键词区分多块板。
6. 页面是状态展示，不是唯一事实来源。故障判断应综合日志、PLC/CNC实时值和物理现场。

| R6104 写入异常 | ✅ Error | ✅ | **保留**在失败阶段 | ✅ 从断点续接 |

> `_forkPhase` 保留在失败阶段是设计意图——恢复后状态机从断点继续，不需要从头重来。

#### 不弹窗不暂停

### 18.6 弹窗级别说明

| 级别 | 含义 | 引擎行为 | 恢复方式 |
|:--:|------|---------|---------|
| ✅ **Error** | 需要人工确认的故障 | 暂停引擎 | 人工处理后点"启动" |
| ⚠️ **Warning** | 已自动恢复，仅通知 | **不暂停** | 无需操作 |
| ❌ 无 | 自动恢复/不影响运行 | 不暂停 | 自动 |

### 18.7 天车零位保护（独立弹窗，无去重）

所有引擎在派发新任务前（出队前/状态变更前）会检查天车 XYZ 是否连续两次全为零。触发后：

| 异常天车 | 暂停范围 | 弹窗 |
|----------|---------|:--:|
| 天车1或2 | 同时暂停 1号线前端+后端 | ✅ |
| 天车3或4 | 同时暂停 2号线前端+后端 | ✅ |
| 天车5（研磨） | 仅软暂停研磨引擎 | ✅ |

> 此弹窗无去重——每次启动/恢复前都会重新检查，触发即弹。
