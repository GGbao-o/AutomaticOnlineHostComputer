## 1. 项目一句话介绍

**制造产线自动化上位机系统**：面向多工序生产现场的 Windows 上位机，负责生产任务管理、工件流转、设备监控、自动调度、异常告警、人工恢复及多设备通信协同；覆盖天车、机械手、货叉、打标机、双头镗、斜床、动平衡、研磨机及 PLC 等设备。

### 简历短版（推荐）

基于 C# / .NET 8 / WPF 开发多设备自动化产线上位机，参与整线业务流程建模、PLC 与 CNC 通信集成、设备互锁、工件状态一致性控制及现场软硬件联调。

### 面试展开版

系统既要读取 PLC 的实时物理信号，也要维护每块工件的软件身份、工艺参数和流程阶段。核心难点不是单台设备控制，而是多条线、多台搬运设备并行时，保证“现场实际位置、工件归属、软件状态和下游握手”在正常与异常场景下均可追踪、可恢复、不可误派发。

## 2. 专业技能与技术栈

### 客户端与工程化

- **C# / .NET 8 / WPF**：Windows 工业上位机开发，使用 XAML 构建设备看板、任务管理、参数配置、手动操作与运行诊断页面。
- **MVVM**：通过 ViewModel、Command、数据绑定组织 UI 与业务逻辑，降低页面与设备控制逻辑的耦合。
- **依赖注入与分层设计**：使用 `Microsoft.Extensions.DependencyInjection` 管理客户端、设备服务、流程引擎与页面依赖；按通信层、设备服务层、流程引擎和展示层拆分职责。
- **MySQL 数据访问与 JSON 配置**：维护设备、工位、工艺及任务相关数据；通过配置文件管理运动参数、超时阈值、报警与监控参数。
- **异步编程与并发控制**：使用 `async/await`、`CancellationToken`、`SemaphoreSlim`、`ConcurrentQueue`、`ConcurrentDictionary` 处理设备轮询、流程调度、通信串行化和异常收尾。

### 工业通信与设备集成

- **Modbus TCP**：对接部分 PLC / 辅助设备，完成寄存器与线圈读写、连接管理、超时处理及状态轮询。
- **三菱 MC 协议**：完成 PLC 的位、字寄存器读取及控制命令写入；针对读—改—写场景进行并发串行化，避免同一字的更新相互覆盖。
- **FANUC FOCAS / Syntec CNC**：参与 CNC 状态、报警、工艺信号和上下料握手集成；理解设备 SDK 或原生句柄的线程约束及通信失败边界。
- **文件握手**：处理打标设备请求/完成文件的交互流程及超时异常。
- **PLC 信号与外接传感器联调**：可基于位信号、寄存器、通信日志和业务状态定位设备反馈、信号极性、时序不一致等问题。

### 自动化业务与可靠性设计

- **有限状态机**：把取料、持件、放料、下游交接、归位等动作拆为显式阶段；区分“命令是否已发送”“是否拿到现场证据”“工件所有权在哪一侧”。
- **FIFO 调度与工件账本**：以队列保证生产顺序，以缓存/账本保存工件身份和工艺参数，避免仅凭 PLC 有板信号猜测工件信息。
- **并发互锁与死锁规避**：按设备锁、碰撞区域锁、目标位置锁建立互斥边界，并统一多锁获取顺序。
- **异常恢复与可观测性**：围绕运动超时、通信失败、取放料结果不确定、设备报警等场景输出可定位日志、告警信息和人工恢复入口。

## 4. 技术难点与亮点（面试重点）

### 4.1 多设备并发互锁：安全与吞吐不能只选一个

**难点**：前后天车会进入相邻区域；同一中转架、斜床边界或下游缓存位可能被不同流程竞争。如果只设置一把“大锁”，虽然简单但会让无冲突动作也被阻塞；如果锁粒度过细、获取顺序不统一，则可能产生死锁。

**处理思路**：

1. 按资源边界拆分为设备独占锁、相邻碰撞区锁与目标位置锁；例如把“打标机—中转架”和“中转架—斜床”拆成不同区域锁。
2. 约定统一锁顺序：`设备自身锁 → ZoneMT → ZoneTS → 目标位置锁`，禁止反向等待，规避循环等待条件。
3. 使用动作租约记录本次动作**实际获取**的锁；正常 `finally` 与应急入口均按记录进行幂等释放，避免通过锁计数“猜测”持锁状态而误释放其他流程的锁。
4. 以现场安全状态作为提前释放条件：设备 Z 轴回到安全高度后，允许释放无关区域锁，让其他无碰撞动作提前并行；同时明确“软件锁已释放不等于设备已物理归位”。

**可写成简历的一句话**：设计并优化多设备并发互锁策略，通过分区锁、统一锁顺序及异常幂等释放，兼顾相邻设备碰撞防护与产线并行效率。

### 4.2 工件状态一致性：不能只相信 PLC 的“有板”信号

**难点**：PLC 信号能说明某位置“可能有板”，但并不包含工件序号、长度、工艺参数等身份信息。通信抖动、下游状态变化或动作中断时，若队列和现场状态处理不当，容易造成重复派发、误取、错误回滚或工件丢失。

**处理思路**：

1. 使用全局 FIFO、线路缓存、设备当前工件、工位账本和下游 Pending 状态保存工件身份与流程上下文。
2. 将关键动作拆成“预检 → 来源预占 → 物理取料确认 → 目标交接 → 提交完成”阶段；只有在确认关键现场反馈后才迁移工件所有权。
3. 调度前先进行候选判断，获得资源后重新读取 PLC 与目标设备状态；满足二次校验才出队和写入目标状态。
4. 若在提交前失败，保持来源状态或把同一工件回滚到队头；若命令已发送但结果未知，则冻结流程并要求人工确认，而不是盲目重试或回滚。

**可写成简历的一句话**：通过 FIFO、工件账本、预占—提交—回滚和现场二次确认机制，保障 PLC 物理信号与软件工件身份在异常场景下的一致性。

### 4.3 异常处理：区分“没执行”和“执行结果未知”

**难点**：工业现场的通信超时不等于设备没有执行命令。例如已下发充磁、退磁或移动命令后连接中断，软件无法直接判断工件仍在来源、已在载具上还是已到目标。

**处理思路**：

- 区分 `NotSent`、`SentAwaitingEvidence`、`Confirmed`、`ResponseUnknown` 等命令证据状态。
- 以 X11 等现场反馈确认是否持件；只在明确没有发送物理命令且来源状态可信时允许自动重试。
- 对“可能已执行但结果未知”的动作暂停引擎、保留工件账本与日志，交由现场人工确认；避免再次取料、重复放料或错误清理状态。

**可写成简历的一句话**：建立面向工业通信不确定性的异常分级机制，基于命令证据和现场反馈控制自动重试、流程暂停及人工恢复，降低重复执行风险。

### 4.4 现场安全信号与运动保护

**项目涉及的典型信号/保护**：

- 取料前确认磁吸传感器无残留工件，充磁后以 X11 等反馈确认工件是否真正被载具持有。
- Z 轴下降过程中监测下压信号；出现异常压力时先停止运动、核对实际坐标和容差，再决定恢复或暂停。
- 线路启动、恢复和领取新任务前检查 XYZ 回零状态，连续读取排除瞬态误判，避免掉电后坐标丢失仍自动运行。
- 对运动超时、伺服报警、位置读取失败设置暂停和人工确认边界，不以“软件流程继续”替代现场安全确认。

## 5. PLC / 现场 / 跨专业对接经验

### 对接内容

- 与 PLC 工程师共同确认设备 IP、寄存器地址、位信号语义、读写权限、脉冲写入方式及轮询频率。
- 围绕“请求—应答—完成—复位”梳理握手时序，明确每一个信号由哪一端置位、何时清零、超时后由谁处理。
- 结合生产现场确认传感器安装位置、信号极性、机械动作顺序和安全边界，避免仅按纸面地址开发。
- 通过上位机日志、PLC 在线状态、设备页面和现场观察联合定位问题，并输出可执行的修改建议或验收步骤。
- 在需求变更或异常复盘后，同步更新寄存器映射、协议文档和业务流程说明，降低口口相传带来的维护风险。

### 简历表述

参与上位机与 PLC/CNC 的联合调试，对接 PLC 工程师完成寄存器映射、握手时序、传感器反馈和异常边界确认；能够结合现场信号、通信日志与业务流程定位软硬件协同问题。

### 面试时可以这样讲

“我不是 PLC 程序的主开发，但会把上位机需要依赖的信号和时序拆清楚：这个信号代表什么物理事实、由谁置位、什么时候复位、丢失时软件该等待还是暂停。现场发现问题时，我会对照 PLC 实时值、上位机日志和当前动作阶段判断是通信、信号、机械状态还是软件状态机的问题，再和 PLC 工程师一起闭环。”

## 9. 面试追问的准备方向

1. **为什么需要锁，锁的粒度如何设计？**
   - 回答重点：共享资源、碰撞区域、目标位置；统一顺序避免死锁；安全高度后提前释放无关锁提升并行度。
2. **PLC 信号和软件状态不一致怎么办？**
   - 回答重点：不以单一信号猜工件身份；保留账本；二次校验；结果未知时冻结并人工确认。
3. **通信超时怎么处理？**
   - 回答重点：区分未发送、已发送待确认、结果未知；命令可能已生效时不能盲目重试。
4. **你和 PLC 工程师如何协作？**
   - 回答重点：地址表、时序图、信号责任方、超时边界、现场联调和文档闭环。
5. **AI 在项目中的作用是什么？**
   - 回答重点：提升实现与分析效率；需求边界、协议约束、代码审查、现场验证与最终决策由自己负责。
